## 1 · 样式载体分布（实测）

| 样本 | 链接样式表 | 段级 class | 内联 style | 关键观察 |
|---|---|---|---|---|
| 人类简史 | 2 份（`stylesheet.css` 10.7KB + `page_styles.css`） | 章内 `p.calibre…` 大量用 | 抽样章 0 处 | 字号全走 **em 相对值**（1.88889em/1.33333em/1.125em/0.75em），色少而精（`#6c483e` 标题、`background-color:#c4aa87`） |
| 阿加莎大全集（85 册） | **85 份**（每册一 `style00NN.css`，~9KB） | `p.ch`（bold+1.3em）、`blockquote` 等 | 少量 `style=";color:black;"` | 色进 class 规则（`color:#005da4`、`color:#ffffff`）；字号 em 为主 |

**结论 A**：完整档必须吃「链接样式表 + class 级联 + 内联 style」三层，缺一层就复现不了微信阅读的分层上色；
85 册 85 份 CSS 说明**按文档解析并缓存章级样式表**不可省（不能假设全书一份）。

## 2 · 脏数据清单（解析器必须容忍）

1. `style=";color:black;"`——**值以分号起头**（空声明），切分要滤空段。
2. `font-weight: blod;`——上游拼写错误，非法值必须**静默回落**而不是整条规则作废。
3. `@font-face` 大段 `src: local(...)` 链 + 残缺 url——本项目不随包字体（LH-F01 已拍板），`@font-face` 整块可跳过，
   但 `font-family` 引用名要能对上 class 规则里的族名（不影响颜色/字号抽取）。
4. 单位混杂：`em`（主流）、`pt`、`px`、`%`——**em 乘用户基准字号**（这是与「外观字号滑杆」共存的关键）；
   pt/px 换算后钳制到合理区间（0.6×~2.5×），超界视同缺失。

## 3 · 与既有口径的撞面点（实现批必须处理）

- **深色调和**（拍板④）：`color:#ffffff` 这类「为白底彩块设计的字色」在无背景渲染下直接隐身——
  调和规则不能只做「压暗/提亮」，要先测**与当前主题底色的对比度**，不达标即回落到「同色相调明度」，
  再不行回落主题正文色。浅色主题同理（`#6c483e` 深棕在米色底可读，在黑底要提亮）。
- **测量与渲染同源**（红线）：em 字号进 span 后，`EpubPager.paraHeight` 与 `_textSpan` 必须吃同一份
  runs→TextStyle 换算（`paraStyle` 现有通道扩参，不许两处各算）。
- **简繁转换逐字等长**：runs 的字符区间在 `paraBody` 通道下不变（转换器只换字不改长），预研确认无冲突。
- **注释体小字（R3-2①）与颜色（本批）叠加**：`annotation` 段的 0.9× 字号要与原书 em 字号相乘而非互斥，
  优先级要在工单里钉死。
- 分页表指纹/快照版本：runs 改变上屏排版 → `PagStore.tableVersion` 与 `DocStore.snapVersion` 双升（F01 §3 已写）。

### 5.2 新增脏数据与硬约束（§2 清单之外）

1. **`body { writing-mode: vertical-rl }`——原书是竖排直排**。微信阅读截图里是横排，说明它也忽略了这条。
   我们**不跟竖排**（要拍板确认，见 §5.4），但解析器必须**见到不认识就跳过**而不是报错。
2. **颜色全是 CSS 命名色**（navy/DarkGreen/maroon/DimGray/Purple/SaddleBrown/White/white），
   本包**零个 `#rrggbb`** → 抽取器必须带命名色表（至少 CSS4 全 148 色），只写十六进制解析＝这本书一条颜色都读不到。
3. **字号单位是 `rem` 不是 `em`**（1/1.5/0.88/0.75/0.6rem）。rem＝相对根字号＝我们的「用户基准字号」，
   语义正好，但要在文档里钉死换算口径；`pt/px/%` 仍按 §2.4 钳制 0.6×~2.5×。
4. **logical margins 带 webkit 前缀**：`-webkit-margin-start/-end/-before/-after`（注的缩进与左右边距全靠它）。
   只认 `margin-left/right` 会丢夹注的层级缩进。
5. **`background-color` 也是原书语义**（`.ji`/`.kong` 灰底白字）→ 深色调和（§3 第一条）不能只调 `color`，
   否则白字标签块在深色主题下直接隐身。

### 5.3 性能地雷（决定抽取器的裁剪策略）

`part0007.xhtml`（卷一首篇）＝114 KB 标记 / 25.8 KB 正文，**151 段平均 20.5 个 span、最多 128 个**；
全书 span 合计 **672,124** 个。现有 `grab()` 把内联元素压平，改成 span runs 后测量与分页成本会按段内
runs 数放大。→ **规格建议：只保留"带排版语义"的 span**（有 color / font-size / font-weight / 背景者＝
本表的 note 系·comment·reign-title·ji·kong），**纯装饰线（`.name`/`.name1`/`.book-title`）不进 runs**，
按语义类白名单裁剪后本书 span 数从 672k 降到约 10 万级（注＋校勘＋按语＋纪年）。
专名线与书名线要做就是**二期专项**（Flutter 侧是 `BorderSide`/自绘下划线，不是 TextStyle 能表达的）。

### 5.4 拍板记录（2026-10-03 产品）

**总原则**：**完全按原书展示**——注释、校勘、史评、纪年、专名线、色块标签……原书怎么排就怎么排；
**将来再来别的精编本书，不许为它定制代码**（这条是本轮拍板的落点，也是判断实现是否合格的唯一标准）。

**由总原则推出的实现红线**：解析器只按 **CSS 声明语义** 通用处理，属性白名单＝
`color` / `background-color` / `font-size` / `font-weight` / `font-style` / `text-indent` /
`margin-*`（含 `-webkit-margin-start|end|before|after`）/ `text-align` / `border*`（专名线就是
`border-left`/`border`）/ `-webkit-text-combine`。**禁止写「class 名→样式」映射表**——
`.note`→绿 这种特判一旦进代码，换一本 class 名不同的精编书就全线失效，直接违反总原则。
本节 §5.1 那张表是**画像证据**（证明"信息在包里、以 class 级联承载"），不是实现依据。

逐条答复：

1. **竖排（`writing-mode: vertical-rl`）＝不跟**。Flutter 没有原生竖排文本布局，做它是另一个量级的工程；
   你拿来做对比的微信阅读同样是横排显示（它也只取颜色与字号）。真要竖排＝另立专项、重开需求。
2. **专名线 / 书名线（`.name`/`.name1`/`.book-title`，55 万处）＝要做**，走通用 `border`/`background`
   通道（不是通鉴专属分支）。我原先建议的「按语义 class 白名单裁剪、装饰线划二期」**作废**——那是特判思路；
   裁剪判据改成**按声明属性**（有上述白名单属性者进 runs）。性能这条不许口头承诺：
   实现批必须先量 67 万 span 下的分页耗时基线，超预算先立性能专项再谈上屏。
3. **开关＝一个总开关「跟随原书样式」，默认开**（开＝原书语义叠加在用户主题之上；关＝回到 R3-2 止血全主题色）。
   不拆「颜色 / 字号」子开关（配置面翻倍且无诉求）。默认值可在原型门逐屏确认时改。
4. **`.comment`（臣光曰整段蓝）与 R3-2①「注释体＝正文色＋小一号」冲突时**：开关开＝**原书优先**（蓝＋1rem），
   关＝止血口径。

仍欠一步：以上只到规格，**原型门未过**——`?r32=anc` 系屏要画出五层对照＋专名线示意、开关进外观弹层，
经产品逐屏确认后才动实现（F01 工单 §3 硬序）。
