## 一 · 配置类提速的同场景对照实验

**元信息**

| 项 | 值 |
|---|---|
| 域 | engineering（性能 / 构建 / CI 方法论） |
| 问题 | 「加了两个开关，没人说得清快了多少、快在哪个开关上」 |
| 方案核心 | 固定场景 + 一轮只改一个变量 + 必须有「全关同场景对照组」+ 段行读数 + 首次成本与稳态成本分开记账 |
| 成本 | 一个 bash 模板（约 20 行），每轮一次完整构建 |
| 本项目出处 | `docs/本机构建环境优化操作指导-20260930.md` 附 B/附 C；落地物 `android/gradle.properties`（提交 `78d4cdb`） |

**本篇从本项目抽到的硬数据**（20 核 · Gradle 8.14 · 全新 worktree 从零出三包）：
`parallel=true` 398.4 s → **157.1 s（−61%）**；`caching=true` 首次喂缓存 +25.5 s，
同输入重出包 → **72.5 s（−82%）**；而「杀软排除 + 缓存盘迁移」两项环境改动对冷构建 **−1.4 s（零收益）**。

**为什么值得抄**：本会话两次把自家 `du`/`find` 掺进计时里，第一次得出「环境优化收益 0」的**假阴性**，
第二次得出「开缓存让构建慢 3 倍」的**假结论**——两个都差点进文档。方案里的 R5/R6 就是把这两次错误固化成红线。

## 二 · 棘轮式守护用例在多写者下的维护口径

**元信息**

| 项 | 值 |
|---|---|
| 域 | engineering（测试 / 守护 / 协作 / CI） |
| 问题 | 登记型守护（超标要登记、登记值只许减）在多写者下频繁报「我没动为什么红」，久了大家学会给红灯找借口 |
| 方案核心 | 四类判定 `over / grown / shrunk / stale`，红灯只留「变坏」；`shrunk` 降级为带收敛命令的提醒；自证三件套（扫描面下限 + 合成样本正对照 + 白名单失效检查） |
| 成本 | 每条规则一张登记表 + 一条 dump 命令 |
| 本项目出处 | `test/size_budget_test.dart`、`test/catch_log_guard_test.dart`、`test/todo_trash_guard_test.dart`、`test/architecture_test.dart`（提交 `7612d0c`）；盘点过程 `docs/用例清理清单-20260930.md` |

**本项目触发这条口径的具体事故**：并行会话把 `user_settings.dart` 的静默 catch 修好、把 `todo_edit_sheet.dart` 拆小，
两次都让**我的**门禁变红（登记值 > 现值即 `shrunk` 判红）。改判提醒后，`over / grown / stale` 仍然拦得住真正的回潮。

**顺带沉淀的判定法**（R9~R13）：用例「默认不删」，只有能证明「同一断言 + 同一被测路径 + 严格子集」才删；
合并只对纯函数成立；守护内部重复遍历要合并但**别按提速立项**（实测省 1~3 秒）；批跑一片红先核文件名。

## 三 · Flutter Android 包体归因与压缩判定

**元信息**

| 项 | 值 |
|---|---|
| 域 | mobile（Flutter / Android 构建产物） |
| 问题 | 「包能不能再小一点」→ 直觉开 R8，做完只动 1% 还引入 keep 规则维护成本 |
| 方案核心 | 先出五类占比账本（Dart AOT / 引擎 / 三方 so / dex / 资源模型），手段必须对齐它作用的条目；三方 SDK **按功能定价**交给产品 |
| 成本 | 一条 `unzip -l` |
| 本项目出处 | `docs/APK包体压缩可行性-20260930.md`（0.2.3+4035 arm64 包实测） |

**本项目账本**：`libapp.so` 42.6% + `libflutter.so` 28.0% = **71% 构建配置动不了**；
dex 只占 9.5%，开 R8 后 **3.59 MB → 约 4.20 MB（负收益，未采纳）**，且必须先补
`-dontwarn com.google.android.play.core.**`（ML Kit 缺 Play Core 会报 12 条 Missing class）；
真正还能动的只有扫码那一套（`libbarhopper_v3.so` 4.9 MB + 3 个 tflite 0.88 MB ≈ **15%**），
而它全库只被 `lib/features/read/presentation/biblio/isbn_scan_page.dart` 一处使用——属功能取舍，不属打包技巧。

## 推送手法备忘（下次照做）

1. Gitee 侧用**浅克隆直推**最省事：`git clone https://gitee.com/chistoiy/developSummary.git` → 落文件 → commit → push
   （凭据走 git credential store，不需要 token）。
2. GitHub 侧浅克隆推不动（`shallow update not allowed`），仍用 `gh api -X PUT repos/.../contents/<path> --input payload.json`，
   payload 由 `tools/ds_push.mjs ghpay` 生成（中文 base64、message 英文）。
3. ⚠️ **行尾陷阱**：从克隆工作副本直接 base64 上传会把 **CRLF** 写进 GitHub 的 blob，而 Gitee 侧 git 已归一成 LF
   → 两端 sha 不等。README 上传前先 `tr -d '\r'`，并用 `git hash-object` 与两端返回值三方对齐再收工。
4. 改 README 索引用带护栏的脚本（命中断言 + 每行 7 段列数校验 + 行数增量校验），**且脚本不幂等，别跑第二遍**。
