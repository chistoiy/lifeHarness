## 二、为什么这三块 core 优先于 11 个 feature

1. **core/database**：schema 迁移与数据修复是跨设备排查的唯一线索，目前炸机只留全局兜底的一行异常，
   没有版本号与影响行数——V1.4x 多次「升级后数据不对」类反馈都缺这条。
2. **core/backup**：`.lhbak` 导出/导入/口令校验失败现在完全静默，用户侧表现为「备份没生效」。
3. **core/notifications**：通知排程降级链（精确闹钟→普通→被系统杀）按设计要可查，目前无从取证。

feature 侧多为「表单写库 + 列表渲染」，异常基本会被全局捕获；补日志的价值在**业务上下文**
（哪个实体、哪次操作），按模块随批补即可，不必专项突击。

## 四、是否加架构守护（待拍板）

候选规则：`features/*/data/**` 与 `core/**` 内的 `catch (` 块中必须出现 `AppLog.` 调用，
否则 `architecture_test.dart` 判红（R9）。

- 优点：空档不会再长回来。
- 代价：现网 catch 数量大（含大量有意吞掉的清理型 catch），首跑会一片红，
  需要「白名单 + 逐批收敛」，本身会产生一次大 diff，与「纯移动」纪律冲突。
- **建议**：先按 L1~L5 铺完再上守护；过渡期用软约束＝本单 + §2.3 + PR 自查项
  「新增 catch 是否记了日志」。等你点头我再进 `architecture_test`。

## 五、拍板结论（2026-09-29 · 产品负责人）

1. **L1 开工** → 已交付（见 §三 L1 行）。
2. **架构守护「catch 必带日志」暂不上**，等 L2~L5 铺完再上；过渡期沿用软约束（本单 + 计划书 §2.3 + PR 自查「新增 catch 是否记了日志」）。
3. **L2~L5 按序排后**，每批独立走三门禁（analyze 基线 / 模块 mini 池 / 全量 run_gate），维持「只加日志零行为改动」纪律。
   - **L2 已交付（2026-09-29）**：纪律守住——`catch (_)` 改 `catch (e)` 只为把异常写进日志文本，控制流一字未动；新增日志一律走 `AppLog`，未开第二条通道。
   - **L3 已交付（2026-09-29 续批）**：同纪律。三域里 calendar/todo 原本**零 catch**（异常直接抛给 Riverpod 吞成 `AsyncError`，UI 侧 `valueOrNull ?? 默认值` 表现为「空列表/角标 0」），所以新增点分两类：失败路径一律 `catch (e)` 记完 `rethrow`（控制流未动），成功路径只补 key 汇总行。**自证口径再补一条**：Provider 体内的失败日志必须按文案去重——失败态每次 rebuild 都会重跑 provider，不去重会刷屏；FakeAsync 下 `AppLog` 的 300ms 节流 Timer 要显式推进才到期，故 settle 之后补一次 `helpers.dart` 新增的 `drainLogTimer(tester)`（`time_v152_test`／`g1_back_probe_test`／`dashboard_days_items_test` 三处，顺带暴露这三处都没 override 待办仓储、读取其实一直失败并被当成空列表）。
4. 交付门新增一条自证：**来源归类必须核对**——异步回调（如 sqflite `onCreate/onUpgrade`）的调用帧里没有业务帧，`_deriveSrc` 会落到「系统」，需要时显式带 `src`。
