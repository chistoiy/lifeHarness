## 二、为什么这三块 core 优先于 11 个 feature

1. **core/database**：schema 迁移与数据修复是跨设备排查的唯一线索，目前炸机只留全局兜底的一行异常，
   没有版本号与影响行数——V1.4x 多次「升级后数据不对」类反馈都缺这条。
2. **core/backup**：`.lhbak` 导出/导入/口令校验失败现在完全静默，用户侧表现为「备份没生效」。
3. **core/notifications**：通知排程降级链（精确闹钟→普通→被系统杀）按设计要可查，目前无从取证。

feature 侧多为「表单写库 + 列表渲染」，异常基本会被全局捕获；补日志的价值在**业务上下文**
（哪个实体、哪次操作），按模块随批补即可，不必专项突击。

## 三、分批建议（每批一批交付、走三门禁）

| 批 | 范围 | 落点 | 验收 |
|---|---|---|---|
| L1 | core/database + core/backup | 迁移每条前后 `addKey`；备份导出/导入/校验失败 `warn/error` | 日志页「数据库」「备份」来源可筛出真条目；新增 2 例断言 catch 路径落日志 |
| L2 | core/notifications + core/ai + core/media | 排程结果与降级链；AI 调用失败与熔断；图片哈希/清理失败 | 触发一次降级/失败即可在日志页看到带上下文的一行 |
| L3 | ledger + calendar + todo（高频三件套） | 导入批次结果、账单解析失败、逾期扫描异常 | 真机跑一次导入，日志页可复盘全过程 |
| L4 | care + habit + journal + inbox | 记录写入失败、打卡结算、同步前清洗异常 | 同上逐模块抽查 |
| L5 | days + goals + items + dashboard | 目标/日子计算与聚合异常 | 同上 |

**每批纪律**：只加日志、零行为改动（与治理「纯移动」同级对待）；`diff` 里出现逻辑改动即回退。

## 四、是否加架构守护（待拍板）

候选规则：`features/*/data/**` 与 `core/**` 内的 `catch (` 块中必须出现 `AppLog.` 调用，
否则 `architecture_test.dart` 判红（R9）。

- 优点：空档不会再长回来。
- 代价：现网 catch 数量大（含大量有意吞掉的清理型 catch），首跑会一片红，
  需要「白名单 + 逐批收敛」，本身会产生一次大 diff，与「纯移动」纪律冲突。
- **建议**：先按 L1~L5 铺完再上守护；过渡期用软约束＝本单 + §2.3 + PR 自查项
  「新增 catch 是否记了日志」。等你点头我再进 `architecture_test`。
