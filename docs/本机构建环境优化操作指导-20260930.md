> 背景实测数据（2026-09-30 采集，作为改动前基线）：
> 机器 20 核 / 29.7 GB 内存（可用 10.8 GB）；**D 盘剩 204 GB（已用 73%）· C 盘只剩 35 GB（已用 83%）**；
> `C:\Users\chist\.gradle` 占 **15 GB**；本项目主工作区 `build/` 3.7 GB，每棵 git worktree 各带 1.3~1.5 GB `build/`。
> 构建耗时基线：三包 release **219.3 s**（缓存热）/ **330.6 s**（冷）；全量门禁独占 **11 分 59 秒**（1795 例），
> 多会话并发时曾被拖到 **72 分钟**。
>
> 下面三件事都需要**改系统/用户环境或管理员权限**，AI 会话不代做；每件事都给了「验证」和「回滚」。
> 建议顺序：**二 → 一 → 三**（先加杀软排除，收益最大且零风险；再迁 Gradle 目录；最后换镜像变量）。

## 一、把 Gradle 用户目录从 C 盘迁到 D 盘（腾出 15 GB）

**为什么**：Gradle 的依赖缓存、wrapper 发行版、构建缓存全在 `C:\Users\chist\.gradle`（15 GB）。
C 盘只剩 35 GB 时，Windows 在低空间下文件系统与分页性能会明显劣化，直接影响构建抖动；
同时它也是本项目最大的一块可迁移占用。

### 步骤（Git Bash / PowerShell 均可，全程约 3~6 分钟）

1. **先停掉所有 Gradle 守护进程和 IDE**（否则文件被占用会移不动）：

   ```bash
   # Git Bash，在项目根执行
   cd /d/dev_workplace/flutter_te/lifeHarness/android
   JAVA_HOME="D:/app_workplace/android_studio/jbr" ./gradlew --stop
   ```

   再确认没有残留 java 进程：任务管理器里 `java.exe` / `openjdk` 应为 0（Android Studio、IDEA 全部退出）。

2. **移动目录**（用 robocopy，可断点续传、处理长路径；PowerShell 或 cmd 执行）：

   ```powershell
   robocopy "C:\Users\chist\.gradle" "D:\gradle_home" /MOVE /R:1 /W:1 /NFL /NDL /NJH /NP
   ```

   退出码 0~7 都算成功（1=有文件被复制）；≥8 才是失败。完成后 `C:\Users\chist\.gradle` 应为空或不存在。

3. **设置用户环境变量**（新开终端才生效）：

   ```powershell
   setx GRADLE_USER_HOME "D:\gradle_home"
   ```

   或者：设置 → 系统 → 关于 → 高级系统设置 → 环境变量 → 用户变量 → 新建
   `GRADLE_USER_HOME` = `D:\gradle_home`。

4. **完全重开终端**（Git Bash 要整个退出重开，不是新开标签页）。

### 验证

```bash
echo "$GRADLE_USER_HOME"                       # 期望输出 D:\gradle_home
du -sh /d/gradle_home                          # 期望 ~15G
ls /c/Users/chist/.gradle 2>/dev/null | wc -l  # 期望 0 或目录不存在
```

再跑一次构建，确认写的是新目录：

```bash
cd /d/dev_workplace/flutter_te/lifeHarness-v158rel
JAVA_HOME="D:/app_workplace/android_studio/jbr" flutter build apk --release --split-per-abi
ls -t /d/gradle_home/caches | head -3          # 时间戳应是刚才
```

耗时应与本文开头的基线（约 220 s 三包）持平或更快；**若明显变慢或报找不到依赖，说明环境变量没生效**（终端没重开）。

### 顺手清掉的垃圾（可选，能再省 1~3 GB）

```bash
# wrapper 里残缺的发行版（本项目已知 gradle-8.11.1-all 只有 .zip.part，不可用）
find /d/gradle_home/wrapper/dists -name "*.zip.part" -print -delete
# 旧构建缓存（超过 30 天的 transforms 派生数据，会自动重建）
du -sh /d/gradle_home/caches/*/transforms 2>/dev/null
```

### 回滚

```powershell
reg delete "HKCU\Environment" /v GRADLE_USER_HOME /f
robocopy "D:\gradle_home" "C:\Users\chist\.gradle" /MOVE /R:1 /W:1 /NFL /NDL /NJH /NP
```

## 二、给 Windows Defender 加排除目录（收益最大，需管理员）

> **2026-09-30 实况更正（执行前必读）**：本机 `Get-MpComputerStatus` 报「无效命名空间」＝ **Defender 处于被动模式**，实际接管实时防护的是 **联想电脑管家（火绒引擎）**（`SecurityCenter2` 注册两条：`Lenovo Anti-Virus powered by Huorong Security` 与 `Windows Defender`；`windefend` 服务在跑但不主导扫描）。**因此本节所有 `Add-MpPreference` 命令在本机不可用也无意义**，排除项要加在联想电脑管家／火绒的「信任区 / 排除项」里。另：本机 Dart 包缓存不在 C 盘，`PUB_CACHE=D:\flutter_cache`（已实测），排除清单以这一条替换 `C:\Users\chist\AppData\Local\Pub\Cache`。

**为什么**：本项目一次 release 构建要读写 `~/.gradle` 里数万个小文件、解包 3.7 GB 的 `build/` 中间产物、
拷 `sqlite3.dll` 之类的原生库。Defender 的实时扫描会对每个写入文件做启发式检查，
这是 Windows 上 Flutter/Gradle 构建慢的第一大外部因素，通常 **20~40%** 的构建时间差来自这里。

### 先确认是不是 Defender 在管（第三方杀软接管时 Defender 不生效）

以管理员身份打开 PowerShell：

```powershell
Get-MpComputerStatus | Select-Object AMProductEnabled, RealTimeProtectionEnabled, AMServiceEnabled
```

- 若 `AMProductEnabled` 为 `True` → 按下面加排除。
- 若为 `False` 且机器上装了 360 / 火绒 / 腾讯电脑管家 → **改到那个软件的「信任区/排除目录」里加同样四条路径**，
  或者干脆退出它再测一次构建时间。

### 加排除（管理员 PowerShell，一次贴完）

```powershell
Add-MpPreference -ExclusionPath "D:\dev_workplace"
Add-MpPreference -ExclusionPath "D:\gradle_home"
Add-MpPreference -ExclusionPath "C:\Users\chist\.gradle"
Add-MpPreference -ExclusionPath "D:\app_workplace\android_studio_sdk"
Add-MpPreference -ExclusionPath "D:\app_workplace\flutter"
Add-MpPreference -ExclusionPath "C:\Users\chist\AppData\Local\Pub\Cache"
Add-MpPreference -ExclusionPath "D:\app_workplace\android_studio\jbr"
Add-MpPreference -ExclusionProcess "java.exe"
Add-MpPreference -ExclusionProcess "dart.exe"
Add-MpPreference -ExclusionProcess "flutter_tester.exe"
```

说明：`D:\dev_workplace` 一条就覆盖本项目与所有同级项目（含各自 worktree 的 build 目录）；
`.gradle` 两条是为了迁移前后都命中；`Pub\Cache` 是 Dart 包缓存（也在 C 盘）。

### 验证

```powershell
Get-MpPreference | Select-Object -ExpandProperty ExclusionPath
Get-MpPreference | Select-Object -ExpandProperty ExclusionProcess
```

然后跑一次构建，把耗时跟基线对比（我这边也可以帮你跑并记录）：

```bash
cd /d/dev_workplace/flutter_te/lifeHarness-v158rel
JAVA_HOME="D:/app_workplace/android_studio/jbr" flutter build apk --release --split-per-abi
# 基线：三包 219.3 s（缓存热）/ 330.6 s（冷）
```

### 回滚（逐条删）

```powershell
Remove-MpPreference -ExclusionPath "D:\dev_workplace"
Remove-MpPreference -ExclusionProcess "java.exe"
```

### 安全边界（别越界）

只排除**开发目录与工具链**。不要把整块 `D:\` 或 `C:\` 根目录加进去，也不要排除
下载目录、邮件附件目录、浏览器下载缓存——那些是真实威胁入口，排除了等于关掉防护。

## 三、把 Flutter 引擎镜像从 tuna 换成 storage.flutter-io.cn

**为什么**：当前用户级环境变量 `FLUTTER_STORAGE_BASE_URL=https://mirrors.tuna.tsinghua.edu.cn/flutter`。
tuna 的 `download.flutter.io` 镜像**缺个别引擎构件**（2026-09-26 实证缺
`flutter_embedding_debug-1.0.0-587c18f8….jar`），Gradle 会报 `Failed to transform / Could not find`，
而且缺位标记会被缓存，`--offline` 也救不回来。当时是靠会话内临时改成
`https://storage.flutter-io.cn` 绕过的——临时变量每次新会话都要重设，容易忘。

### 步骤（普通 PowerShell，不需要管理员）

```powershell
# 1) 看当前值（确认基线）
[Environment]::GetEnvironmentVariable("FLUTTER_STORAGE_BASE_URL","User")

# 2) 改成 flutter-io.cn（该站与 storage.googleapis.com 当时均可直连）
[Environment]::SetEnvironmentVariable("FLUTTER_STORAGE_BASE_URL","https://storage.flutter-io.cn","User")

# 3) 顺手把 Dart 包镜像也定下来（tuna 的 dart-pub 可用，只是会刷 advisories 警告）
[Environment]::SetEnvironmentVariable("PUB_HOSTED_URL","https://mirrors.tuna.tsinghua.edu.cn/dart-pub","User")
```

**完全退出并重开 Git Bash**（用户级变量不会注入已存在的进程）。

### 验证

```bash
echo "$FLUTTER_STORAGE_BASE_URL"     # 期望 https://storage.flutter-io.cn
cd /d/dev_workplace/flutter_te/lifeHarness
flutter precache --android           # 拉全 Android 引擎产物，成功即镜像可用
```

再跑一次**冷构建**（先把某棵 worktree 的 build 目录删掉模拟冷启动）验证不再缺 jar：

```bash
rm -rf ../lifeHarness-r8/build
cd ../lifeHarness-r8 && JAVA_HOME="D:/app_workplace/android_studio/jbr" \
  flutter build apk --release --target-platform android-arm64
```

成功标志：日志里没有 `Could not find flutter_embedding` / `Failed to transform`。

### 回滚

```powershell
[Environment]::SetEnvironmentVariable("FLUTTER_STORAGE_BASE_URL","https://mirrors.tuna.tsinghua.edu.cn/flutter","User")
```

若之前那次缺 jar 的故障被缓存过，改完镜像后先执行一次
`cd android && JAVA_HOME=… ./gradlew --stop` 再 `flutter clean`，避免旧的失败标记继续生效。

### R8 实验结论（已跑完，供决策）

在独立 worktree `lifeHarness-r8` 里开了 `isMinifyEnabled` + `isShrinkResources` 并补了反射保活规则，
出包对比（arm64）：

| | 无 R8（现发布配置） | 开 R8 |
|---|---|---|
| `classes.dex` | 3.59 MB | **4.20 MB（反而更大）** |
| 包体积 | 35.42 MB | 35.62 MB（+216 KB） |

原因：本项目 Java/Kotlin 侧本来就很小（3.6 MB dex 里绝大部分是**各插件自身必须保留的注册入口**，
按保活规则整体 keep 后 R8 无从收缩），而 R8 重写 dex 会带来对齐与元数据开销；
体积大头是 `libapp.so` 16.9 MB（Dart AOT）+ `libflutter.so` 11.1 MB（引擎），**R8 完全碰不到**。
结论：**不开**，`build.gradle.kts` 保持现状，实验 worktree 用完即删。
真要减包体只剩两条路：换纯 Dart 条码解码（省约 5.8 MB，代价是识别率下降），
或接受现状（35 MB 对本地优先、无网络依赖的应用属正常量级）。

## 附 B：实测结果（2026-09-30 · 排除项 + Gradle 迁 D 盘之后）

冷构建对比（同一提交 `fff610d`·`flutter clean` 后 `flutter build apk --release --split-per-abi`·独占无并发）：

| 样本 | Gradle 段 | 总耗时 | 备注 |
|---|---|---|---|
| 基线·优化前冷构建 | 330.6 s | — | v0.2.2 出包时记录 |
| 优化后冷构建（污染样本） | 559.1 s | 573 s | **勿作基线**：测量期间我并行跑了 `du -sh` 遍历 15 GB 目录抢 IO |
| 优化后冷构建（干净样本） | **329.2 s** | **336 s** | 独占重跑·与基线差 −1.4 s（0.4%） |

**诚实结论：这两项改动对构建速度基本零收益。** 冷构建的大头是 CPU 密集的 Dart AOT 快照与 Kotlin/Java 编译，不是杀软扫描能撬动的小文件 IO；杀软排除真正的价值在 `pub get`／解包这类高频小文件环节，而冷构建里那部分只占十几秒。

两项改动的**真实收益在别处**：C 盘腾出 15 GB（删旧目录后从剩 35 GB → 约 50 GB，脱离低空间劣化区）；Gradle 缓存与包缓存都落在数据盘，系统盘满导致的构建抖动消失。

**已核实生效**：优化后那次构建只写 `D:\gradle_home`（`.tmp` / `kotlin-profile` 时间戳 17:51），`C:\Users\chist\.gradle` 全程 0 写入 → **旧目录可安全删除**（删前先 `./gradlew --stop`）。

**可复现性副产品**：同提交重构建出的三包字节数 `37137222 / 34137528 / 39758657`，与发布挂到 GitHub、Gitee 的三包逐字节相同 → 以后核对「线上包是不是这个提交出的」，本地重跑比字节数即可，不必靠 mtime 猜。

**真要提速还剩两条**（当时的判断）：① `android/gradle.properties` 目前只有 `jvmargs=-Xmx8G` 一行，没开 `org.gradle.parallel=true` 与 `org.gradle.caching=true`（20 核机器跑串行任务）；② 发版固定复用同一棵 worktree，别再每次新建冷编译（每棵自带 1.3~1.5 GB `build/`，从零编译）。门禁那 12 分钟的大头是 180 个测试文件各自的进程启动与 widget pump，与本次两项环境改动无关。

① 已在同日按实测落地，数据见**附 C**——这一条才是真提速，前面那两项不是。

## 附 C：`gradle parallel` / `caching` 两开关实测（2026-09-30 · 提交 `7612d0c`）

场景一律按**发版真实场景**测：新开一棵 worktree、`build/` 从零、`flutter build apk --release --split-per-abi`。
同目录重复构建那种增量数字没有参考价值——我们从不那样出包。
读数只取 flutter 自己打的 `Running Gradle task 'assembleRelease'... Ns`（Dart AOT 也在这段里，所以它才是完整口径）。
原始日志：`.walkthrough/_gradlespeed.txt`（临时取证区·不入库）。

| 轮 | 配置 | build cache 状态 | Gradle 段 | 全程 | 说明 |
|---|---|---|---|---|---|
| 轮 5 | 两开关都关（旧默认） | 不读不写 | **398.4 s** | 405 s | 与轮 3 严格同场景的唯一对照组 |
| 参照 | 两开关都关·主工作区 `flutter clean` | — | 330.6 s | 336 s | 附 B 那次·配置相同，差在机器状态 |
| 轮 3 | **parallel 开**·caching 关 | 不读不写 | **157.1 s** | 161 s | 全新 worktree |
| 轮 4 | parallel + caching 开 | **空**（先把 `build-cache-1` 删净重测） | 182.6 s | 186 s | 喂一次缓存 = 比轮 3 多 25.5 s（+16%） |
| 轮 2 | parallel + caching 开 | **暖**（输入与轮 1 逐字节相同） | **72.5 s** | 79 s | 「同一提交换 worktree 重出包」的情形 |
| 轮 1 | parallel + caching 开 | 空 | ~~520.1 s~~ | 527 s | **污染样本·勿引用**：测量期间我自己并行 `du`/`find` 正在膨胀的 build 树，把 186 s 的事读成了 520 s（附 B 同一个错，隔两轮又犯一次） |

**已落地**：`android/gradle.properties` 加 `org.gradle.parallel=true` + `org.gradle.caching=true`（各带一行实测注记）。

- **parallel 是主菜**：398.4 s → 157.1 s，**−61%**。这机器 20 核，之前所有插件子工程的 Kotlin/Java 编译都在串行走。
- **caching 是配菜**：代价是首次喂缓存多花 25.5 s；收益是同样输入再出一遍 157.1 s → 72.5 s（**−54%**）。
  发版流程里「同一提交换 worktree 重出包」「附件挂了要重挂但包要能自证」正是一行不差的重出包情形，划算。
- **两条知情副作用**：① 多会话同时构建时各自都会 parallel，抢 20 核会更明显——`flutter` 全局串行的老规矩照旧，
  别把「构建变快了」当成可以并行的理由；② build cache 会长驻 `D:\gradle_home\caches\build-cache-1`（数百 MB 起涨），
  纯可再生缓存，磁盘紧张时整目录删掉即可，代价只是下一轮多花 25 s。

**仍然最省的一条**：同一棵 worktree 复用着出包，比这两个开关加起来还省（附 B 那条判断不变）。
