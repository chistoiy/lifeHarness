## 二、硬漏（6 条 · 建议并入 V3）

### H1 · 表结构缺「写入态」列 —— UI 多处要求，DDL 表达不出 🔴 最实

- **缺口**：F1-1 的 `nfc_cards` 字段清单＝`id/name/target_kind/target_ref/tag_key/tag_kind/created_at/last_used_at/use_count`。**但全档至少 5 处要求「已写入/未写入」态**：
  - C16「新建保存即落库（状态「未写入」）」；F1-3 列表行「右侧写入态：未写入＝`写入` 小钮／已写入＝灰字」；
  - F2-1「成功后把该行写入态置「已写入」」；§4.2 编辑态「写入卡片」行右侧显示「已写入/未写入」；
  - B6/B7「卡片记录保持「未写入」」。
- **证据**：`grep` 上述 DDL 清单，无任何可承载写入态的列。
- **判定**：**纯靠 DDL 无法实现**。「写入态」不可能每次靠读标签反推（NFC 读取需前台开 reader mode、耗电、且失败态无法与「未写过」区分）。
- **建议补丁（加 F1-1 一列 + 一条裁决）**：
  > **C31（新增）卡片写入态存本机**：Ddl 增 `written_at INTEGER`（**NULL＝未写入**，毫秒时间戳＝最后成功写入时刻）。**判定只读本列**，不靠读标签反推；写卡成功→置 now；换卡覆盖写入→覆盖 now；删除卡片行即随之消失。理由：写入态是**历史事实**（曾写成功过），不是当前标签状态，反推不可行。
  > ⚠ **B29 联动**：UID 轨绑定的卡（`tag_kind='uid'`）**永不写标签**，其 `written_at` 恒为 NULL，UI 须显示「只读卡 · 不可写入」而非「未写入」——否则用户会反复点「写入」撞 B3 只读失败档。

### H2 · 触发点没有 `BuildContext` / `WidgetRef`，而复用路径强制要 🔴 最实

- **缺口**：C22/F2-11/§4.4 要求有状态卡回执「阅读侧结束**复用 `endReadPillTimer`**」。但该函数签名是：
  ```dart
  // lib/shared/linkage/timer_bar_overlay.dart:77
  Future<void> endReadPillTimer(BuildContext host, WidgetRef ref, String bookId)
  ```
  它要 `host` 挂 toast **并**弹 autoAsk 记进度层。
- **证据**：方案 §3.2 的触发链是 `MainActivity.handle(intent) → takeLaunchRoute → app 组合根`，且 §4.4 明写「触发后**不跳屏、不弹层**（除 autoAsk））」。**组合根消费点不是某个已挂载页面的 context**；`WidgetRef` 更不存在（不在 build 作用域内）。
- **判定**：**「复用 endReadPillTimer」与「触发点在组合根」两条不能同时成立**。这不是措辞问题，是实现期必撞的编译错。
- **建议补丁（新增 C32 + B31，并改写 §4.4 一句）**：
  > **C32（新增）有状态卡触发的 host/ref 取法（唯一口径）**：`nfc_mounts` 的两个转发口内部**自取**容器，不接受外部传 context——
  > ① `ref` ＝ `ProviderScope.containerOf(rootContext)` 转 `WidgetRef`（既有先例：`sys_pill_sync.dart:102` 批B 正是「走根 Navigator」跨弹层提交）；
  > ② `host` ＝ 根 `NavigatorState.context`（`navigatorKey.currentContext`），**须在首帧后**（`addPostFrameCallback` 或等 `takeLaunchRoute` 消费完成信号）才取，`context.mounted` 为假则**本轮放弃弹层、只落库**（结束动作已成功，不回滚、不重试）。
  > ③ **autoAsk 弹层取不到 host 时**：按「已结束 + 不弹层」降级，**toast 亦跳过**；下一次在 App 内打开阅读器时由既有 `runningSession()==null` 正常显示，不补偿弹层。
  > ④ 硬前置追加：`takeLaunchRoute` 消费点须**在首帧完成后**才派发（桌面模块批 1 的义务，NFC 侧写进 §6.5 依赖表并列入验收）。
  > **B31（新增）冷启动贴有状态卡、App 首帧未就绪**：落库照做（`startTiming`/`startSession`），**回执与 autoAsk 允许丢失**，不重试、不排队补弹。

### H3 · 备份只说了 `excludeTables`，漏了两处真实登记点 🟠

- **缺口**：C8 只写「进包，**不加** `excludeTables`」。但真实备份链有**三处**表登记，方案只覆盖了其中最不出错的一处（因为全量走实表差集，不登记也自然进包）。
- **证据**：
  1. `lib/core/backup/backup_service.dart:260` 子集备份走 `exportTablesForModules(modules)` ← `lib/shared/linkage/export_units.dart:364` 的 `kExportUnits`。**`nfc_cards` 不在任何 `ExportUnit` 的 `tables` 里** ⇒ 用户「只备份 NFC 相关」时该表**不导出**（子集是差集法：未登记＝归属不明＝不收）。
  2. `lib/core/backup/db_overview.dart` 的表元数据表（`'books'`/`'categories'` 等约 40 项）**无 `nfc_cards`** ⇒ 数据库概览屏不显示该表、备份/恢复报告里它无中文标签。
- **判定**：C8 的字面结论（全量进包）成立，但**「换机后同一张标签仍可用」这个 C8 给出的唯一理由，在子集备份路径下会失效**——而子集备份正是 V1.66 批 2 刚拍板的主推路径。
- **建议补丁**：
  > **C8 补正**：卡片进包需**三处登记齐**，缺任一则视为未进包：① 不加 `excludeTables`（全量差集自然收）；② **`export_units.dart` 新增 `ExportUnit(id:'nfc', tables:[DbSchema.tNfcCards])`** 并登记进子集可选模块清单；③ **`db_overview.dart` 表元数据补 `'nfc_cards': (label:'NFC 卡片', module:'NFC')`**。
  > **F1-1 验收标准补**：备份/恢复链新增常驻断言——`test/backup_scope_test.dart` 增「nfc 单元导出含 `nfc_cards`」＋「`nfc_cards` 不在任何 `excludeTables` 恒定集内」。

### H4 · 卡片 `id` 生成规则未冻结，与 §5.7 容量核算口径打架 🟠

- **缺口**：NDEF 里只存 `lh://nfc/<cardId>`（C1/C2），但 **`cardId` 怎么生成、长度多少，全档未定义**；F1-1 只说 `id TEXT 主键`。
- **证据**：§5.7 容量核算写「单条 URI ≈ **21 字节** ＋ NDEF 开销 ≈ 30 字节」——**21 字节对应的是 8 位左右短 id**。若实现随手用 `uuid4()`（36 字符），URI 变 ≈49 字节、总计 ≈58 字节。NTAG213 用户区 144 字节虽仍够用，但：
  - §5.7 那行**给用户看的核算数字当场失真**（用户会拿它判断卡型）；
  - C8 依赖「标签只存编号」的可读性/可手抄性（P3 虽判不做导出清单，但排障时**人眼要能在标签上认出自己的卡**）。
- **建议补丁**：
  > **C33（新增）卡片 id 生成规则（唯一口径）**：入库时生成 **12 位 base62 随机串**（`0-9a-zA-Z`，`Random.secure()`），如 `k3P9xQaZbT2m`。**禁 uuid/时间戳/自增**（长度不可控、可枚举、泄露创建顺序）。
  > **§5.7 容量核算同步改写**为「单条 URI ≈ 21~24 字节（含 12 位 id）＋ NDEF 开销 ≈ 30~35 字节；NTAG213 用户区 144 字节 ⇒ 余量充足」。标签上**可印一行 8 位短码**（id 前 8 位）供人眼识别，全码在 App 内查看。

### H5 · 四种回执文案与被复用函数的真实文案逐字不一致 🟠

- **缺口**：C22/§4.6 冻结回执文案「《书名》已结束 · 23 分钟」「开始阅读《书名》」。
- **证据**：`endReadPillTimer` 内部真实 toast 文案是（`timer_bar_overlay.dart:87-92`）：
  ```dart
  closed == null ? '《$title》计时已取消' : '《$title》已结束计时 · ${closed.minutes} 分钟'
  ```
  即「**已结束计时**」而非「已结束」，且另有第四态「**计时已取消**」方案完全没列。
- **判定**：方案「禁自造 toast ＋ 复用单源」的红线是对的，但**冻结的文案不是复用后会得到的那句**——这是典型的「断言从方案反推」陷阱，做完会发现实现与冻结档不符。
- **建议补丁**：
  > **C22 补正（文案以被复用函数为准）**：阅读卡回执**逐字沿用 `endReadPillTimer` 既有文案**——结束＝「《书名》已结束计时 · N 分钟」、取消＝「《书名》计时已取消」、开始＝「开始阅读《书名》」（开始侧本模块自造，属新增，须产品点头）。**本模块不为对齐文案去改 `endReadPillTimer`**（单源红线优先）。
  > **时间卡回执**保持自造四态中的两条：「开始「分类」计时」／「已结束「分类」· N 分钟」；**补第五态**：目标已失效但计时在跑（分类被删、计时未收口）→「已结束计时 · N 分钟」并**不报分类名**。
  > **F2-11 验收标准改写**：「回执文案与 `endReadPillTimer` 既有四态逐字一致」而非「按 C22 表」。

### H6 · NFC 是「独立模块」还是「设置子屏」——注册表与需求清单口径冲突 🟠

- **缺口**：需求清单模块 19 标题「**独立模块** NFC 卡片」；方案 C15「不占宫格（低频管理面）」；但原型四屏 `p-sub-nfc` / `sheetNfcEdit` / `sheetNfcWrite` / `sheetNfcDel` 在 `_modules.json` 里 **`home` ＝ `index.html`**，即归在 **settings（设置子屏）** 名下；`docs/模块注册表.md`（生成产物）**没有 nfc 模块行**。
- **证据**：`grep -i nfc docs/模块注册表.md` → 0 命中；`_modules.json` 四屏 `home:index.html`。
- **判定**：屏单一归属规则下现状是自洽的（管理面归设置家），**但「独立模块」这个措辞会误导实现批去建 `lib/features/nfc/` 同时又以为该在注册表加模块行**——`gen_registry.py` 是从 `_modules.json` 生成的，手改注册表会被覆盖/被 doclint 拦。
- **建议补丁**：
  > **C34（新增）模块归属口径**：`nfc_cards` 的**代码归属＝独立 feature 目录** `lib/features/nfc/**`（因有独立 DAO/触发链/页面）；**屏归属＝settings 家 `index.html`**（原型已在位，**不迁专版**，管理面四屏留在壳里）。`docs/模块注册表.md` 由 `gen_registry.py` 生成，**禁手改**；若产品要求注册表出现 nfc 行，须改 `prototype/_modules.json` 的模块划分并重跑生成器＋`proto_registry --check`。
  > 需求清单模块 19 标题「独立模块」补脚注：「**独立 feature 目录，屏归设置家；不占宫格、不进注册表模块行**」。

## 五、一句话结论

## 六、URL Scheme 结合评估（追加 · 2026-10-15 10:25）

### 6.1 现状定性：结合了，但只结合了一半

冻结档 §3.2 定的 NDEF 内容是 URI 记录 `lh://nfc/<cardId>`（C1/C2），所以 **「URL Scheme」在 NFC 方案里已经是既成事实**——这不是待决策项。

但结合的**位置**偏了一层：

| 层 | 桌面模块 | NFC 卡片 | 是否共用 |
|---|---|---|---|
| **存储/寻址格式** | `lh://` ＋ 7 枚 path 白名单 | `lh://nfc/<cardId>` | ✅ 同一命名空间 |
| **分发通道（Action）** | `ACTION_VIEW` ＋ `data scheme="lh"` | `ACTION_NDEF_DISCOVERED` ＋ `scheme=lh/host=nfc` | ❌ **两条路** |
| **原生解析** | `handle(intent)` 查 path 白名单 | 另一分支（待实现） | ❌ 各写一套 |
| **投递 Dart** | `takeLaunchRoute` 单次消费 | 另一通道（待定） | ❌ 两套队列 |

**真实风险**：`MainActivity.handle()`（`android/app/src/main/kotlin/com/lifeharness/lifeharness/MainActivity.kt:68`）已经是一个按 `intent.action` 分派的总入口，且 `launchMode=singleTop` 意味着**NFC 贴卡与 URL 唤起共用同一个 Activity 实例**。方案却把 NFC 排成独立于 `lh/launch` 的第二条链路——与桌面方案 §2.0 那条「**动作表＝唯一入口定义，三端禁止各写一份跳转逻辑**」的实现红线**同一条精神**。同一份 `cardId` 解析/校验/去抖逻辑若写两遍，批 2 一定分叉。

### 6.2 结合能白拿的三个增量（建议纳入批 2）

**① 合流分发（强烈建议 · 修 6.1 的分叉）**
`takeLaunchRoute` 的载荷从 `Map{action, args...}` 扩为可承载 `kind='nfc'` 分支，`nfc_cards` 查表与去抖**只在组合根一处**做。收益不只是省代码：去抖窗口（3 秒）、「已删卡静默忽略」这类口径**只可能有一份实现**，否则「贴卡」和「快捷方式跳转」会给出两种行为。
⚠ **代价要说清**：桌面方案 §4.3 冻结了白名单全集为 7 条且「一字不多」，且 §4.4 明写小组件 `PendingIntent` **走 `lh://` 统一寻址**。NFC 要合流就必须**动桌面方案的白名单条文**（加 `nfc/<cardId>` 形态），这是**跨冻结档改动，需产品拍板**，不是实现批能自行决定的。

**② URL Scheme 独立入口带来的能力（不依赖任何新硬件）**
标签被丢弃/损坏/借出、或换到一台**没写过这张卡**的手机时，只要输入 `lh://nfc/<cardId>` 或点一条这样的链接，同样能触发行程。这是 NFC 方案**零成本的降级通道**，而 §5.7 恰恰已经预设了「标签可能损坏」这个场景。
⚠ 但落地要配套两条，否则是安全口子：
- 桌面白名单必须显式容纳 `nfc/<id>` 形态并**对 `id` 做格式校验**（12 位 base62，见 H4），非法格式静默丢弃，**不得回显 id**；
- `lh://nfc/<不存在的id>` ⇒ 走 NFC 侧既有的「已删卡静默忽略 / 未绑定引导」口径，**不得**掉进 `unknownRouteFallback` 兜底页（那会把内部寻址暴露成用户可见的报错页）。

**③ 反向发现：URL 入口天然支持「同卡多机」——但有个真实前提**
`cardId` 存**本机** `nfc_cards` 表，所以换机后新机库里没有这张卡的记录，直接贴标签/输入链接都会走「未绑定」。这与 H3 说的「进备份包、换机恢复后同一张标签仍可用」是**互为因果的一对**：备份进包（不只是备份，是恢复）才让跨机成立。
→ 建议在 §5.7 选型建议那行补一句：**「同一张卡在多台装了本 App 的设备间通用，条件是那张卡的记录已通过备份恢复过去。」**

### 6.3 结合**不应**做的三件事（防过度设计）

| 不做 | 理由 |
|---|---|
| 开放**任意** `lh://` path 触发任意动作 | 桌面方案 §4.3 已用白名单钉死；扩到任意＝反射式跳转，且 NFC 标签可被任何人写入 |
| 卡片目标改为**直接存 URL 字符串** | 与「标签只存编号」的根本设计冲突：改目标就要重写卡、目标 id 一旦跨机失效标签即变砖；也毁掉 §2.0 动作表单一来源 |
| URL 入口带**参数**（金额/分类预填等） | 桌面侧 `amount` 已是非数即忽略；卡片侧引入参数会立刻触碰「标签被改 ⇒ 静默记账到错误分类」的风险面，收益远小于风险 |

### 6.4 结论

- **能否结合**：已经结合（URI 寻址），且**应当进一步结合**（分发链路合流）。
- **性质**：不是新需求，是把两处已存在的实现分叉收拢——**属修 bug 级，不属加需求级**。
- **唯一阻碍**：桌面冻结档 §4.3 的「白名单全集 7 条、一字不多」需产品点头加 `nfc/<cardId>` 形态。
- **建议裁决编号**：**C36**（合流分发，唯一载荷契约）＋**B35**（`lh://nfc/<id>` 的 id 格式校验与未命中降级）＋**B36**（同卡多机的前置条件＝记录已恢复，明写进 §5.7）。

## 七、桌面快捷方式 × URL Scheme 覆盖度核查（追加 · 10:29）

> 由「桌面快捷方式是否也结合了 URL Scheme」引出。核查结论：**桌面模块内部的四路入口，统一度比 NFC 方案还差一档。**

### 7.1 逐路核查（依据 `桌面模块-冻结版开发方案-20261013.md`）

| 入口路 | 方案条文 | 是否声明走 `lh://` |
|---|---|---|
| **长按图标菜单**（动态快捷方式 F1-2） | §4.1「点击任一 → 走动作表对应路由」 | ⚠ **未声明 Intent 形态** |
| **铺到桌面**（F1-5 `requestPinShortcut`） | §4.2「每行「铺到桌面」→ `requestPinShortcut`」 | ⚠ **未声明 Intent 形态** |
| **小组件**（F1-3） | §4.4「`PendingIntent` **走 `lh://`**，统一寻址」 | ✅ **明确写了** |
| **URL Scheme**（F1-1） | §4.3 链路本体 | ✅ 本体 |

### 7.2 问题定性：桌面模块自身有两处 Intent 形态未定稿

§2.0 动作表末尾那列名为「**Scheme（白名单内）**」，给每枚动作都标了 `lh://inbox/new` 等——很容易让人以为四路都走 URI。**但 §2.0 那列是「本路即 URL Scheme 时用什么 path」的解释，不是「另外三路都构造成这个 URI」的定义。** 方案从未写过 `setDynamicShortcuts` / `requestPinShortcut` 的 `Intent.setData(Uri.parse("lh://..."))`。

这不是抠字眼，有两个实打面的后果：

**① Android 平台侧：`Intent` 不带 data 就走不进 `VIEW` 解析链。**
`setDynamicShortcuts` 与 `requestPinShortcut` 都接受任意 `Intent`。若实现只填 `setAction(Intent.ACTION_VIEW)` 而**不填 data**，则系统会尝试匹配任何 `VIEW` filter——包括既有那 5 组 `content/file` 打开方式 filter（`AndroidManifest.xml:78/97/103`）。结果可能是**「记一笔」快捷方式唤起「打开方式」处理**。这类错配在真机上表现为「点了没反应」或「弹出错误的文件选择」，**开发者极难定位**，因为不崩、不报错。

**② 行为一致性：同一切换动作，从四路进去可能表现不同。**
动作表的「唯一入口定义」红线（§2.0）管的是**目标路由**，管不到**到达方式**。而 §4.7 那张表已经承认到达方式有差异（冷启动 vs 热启动的导航栈行为不同），若 Intent 形态再分叉，`singleTop` 下的 `onNewIntent` 分支就可能只覆盖其中一路。

### 7.3 建议补丁（补桌面冻结档 · 与 §6 的 C36 打包成同一次改动）

> **C37（新增 · 桌面侧）四路入口 Intent 形态统一（唯一口径）**：
> `setDynamicShortcuts`（F1-2）与 `requestPinShortcut`（F1-5）构造的 `Intent` **一律为**：
> `Intent(Intent.ACTION_VIEW, Uri.parse(<§2.0 该动作的 lh:// path>))`，
> 显式 set class 到 `MainActivity`，`flags = FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP`。
> **禁**只 setAction 不 setData（会误匹配既有 5 组打开方式 filter）；**禁**自定义 action（会绕过 `VIEW` 解析链，多出一条分叉）。
> 由此四路（长按菜单／铺到桌面／小组件／URL）**共用同一份 Intent 构造与同一份 path 白名单**，`handle(intent)` 的 `ACTION_VIEW` 分支**一处**消化全部。
>
> **B37（新增）冷启动时 `handle(intent)` 早于 `configureFlutterEngine`**：现有实现已在 `configureFlutterEngine` 内调 `handle(intent)`（`MainActivity.kt:117`）保证不漏，但**必须补一条测试/验收**：冷启动贴卡或点快捷方式时，意图必须**先入队**、Dart 侧引擎就绪后再由 `takeLaunchRoute` 单次消费——**禁**在 Dart 未就绪时丢弃（既无首帧也无组合根的路径）。此条与 §6 H2④ 同源。
>
> **验收补**：长按菜单 4 枚、已铺快捷方式、小组件点击、`adb shell am start -a android.intent.action.VIEW -d "lh://ledger/add"` 四种方式进同一动作，**导航栈结果逐字一致**（均直达 `/ledger/add`，冷启动无返回栈）。

### 7.4 对 §6 结论的修订（重要）

§6.1 那张表把桌面侧记为「✅ 已结合」，**现更正为「⚠ 部分」**：

| 层 | 桌面模块 | NFC 卡片 |
|---|---|---|
| 寻址格式 | ✅ `lh://` ＋ 7 枚 path（§2.0 已列全） | ✅ `lh://nfc/<cardId>` |
| 分发 Action | ⚠ URL/widget 走 `VIEW`；**快捷方式两路未定稿** | ⚠ `ACTION_NDEF_DISCOVERED`（已定） |
| 原生解析 | ⚠ 仅 `VIEW` 分支会走；快捷方式是否抵达**取决于实现是否 setData** | ❌ 独立链路 |
| 投递 Dart | ✅ `takeLaunchRoute` | ❌ 待定另一条 |

**净结论**：这不是「NFC 单方面没结合」，而是**桌面模块自己先留了个洞（C37 要补），NFC 只是把同一个洞暴露得更明显**。
因此 **C36 与 C37 应作为一次改动一起拍板**——先在桌面侧定死「四路统一构造成 `ACTION_VIEW` ＋ `lh://` URI」，NFC 侧只需把 `ACTION_NDEF_DISCOVERED` 的 `data` 交给同一个解析分支，**一行额外分支都不必多写**。这是本次查漏补缺中**投入产出比最高的一条**。

## 八、「以 URL Scheme 为核心」架构提议的评估（追加 · 10:30）

> 产品提议：把 `lh://` 立为**核心**，NFC／快捷方式／小组件等皆为其外围功能。**方向正确，但「核心」须精确到层，否则会做过头。**

### 8.1 关键先例：项目里已有一条「刻意不走 URL」的链路

`MainActivity.kt:688-692` 已有两个自定义 action：

```kotlin
const val ACTION_PILL_END  = "com.lifeharness.pill.END"
const val ACTION_PILL_NOTE = "com.lifeharness.pill.NOTE"
const val EXTRA_PILL_KIND  = "pillKind"
```

由悬浮窗服务 `TimerPillService.kt:732` 以 `putExtra(EXTRA_PILL_KIND, kind)` 发出（6133/6135 两轮热修承载，**真机在用**）。
它**故意不走** `lh://`，因为悬浮窗点击要带 `pillKind` 且须被 `singleTop` 的 `onNewIntent` 单独识别。

**这条先例是本节最重要的证据**：它证明「什么走 URL、什么不走」在本项目里**已有既成判据**，不是可以一刀切的架构洁癖问题。

### 8.2 结论：URL 是「寻址核心」，不是「分发核心」

分两层看，结论完全不同：

| 层 | 定位 | 覆盖 | 是否该统一 |
|---|---|---|---|
| **L1 寻址/契约层**<br>「我该做什么」＝**唯一字符串** | **✅ 应立为核心** | 动作 id、`lh://` path 白名单、`nfc/<cardId>`、带参形态 | **是**。这层必须是单一真源，否则行为分叉 |
| **L2 传输/分发层**<br>「怎么进到 App」 | **❌ 不该强制统一** | `ACTION_VIEW` / `ACTION_NDEF_DISCOVERED` / 自定义 action / `PendingIntent` / `MethodChannel` | **否**。Android 决定它们，强行统一会与平台语义打架 |

**一句话判据**：**凡「进 App 的路」由平台决定 ⇒ 不可统一；凡「进 App 之后做什么」由本项目决定 ⇒ 必须统一。**

### 8.3 若把 URL 硬立为「唯一分发」（会做过头的地方）

- ❌ **NFC 分发不经过 `ACTION_VIEW`。** NDEF 标签携带的 URI 由系统在 `ACTION_NDEF_DISCOVERED` 里派发，这是 Android 的既定行为，App 无法要求系统改用 `ACTION_VIEW`。若强行统一，等于**要改平台语义**。
- ❌ **后台型动作不经过 URL。** 小组件「勾选打卡」若要**不打开 App**（桌面方案 §4.4 批 3 写的「后台 isolate 执行」）就不能拉起 Activity，只能走 service/自定义 action。
- ❌ **悬浮窗已在用自定义 action**（8.1），改它＝动 6133/6135 热修承载的真机链路，纯风险无收益。
- ⚠ **`Content-Type`/多类型打开方式不能动。** `AndroidManifest.xml:78/97/103` 那 5 组 `content`/`file` filter 属 EPUB/MD 通路，走 `ACTION_VIEW`＋**非** `lh` scheme，硬塞进 URL 命名空间＝污染白名单。

### 8.4 建议的正确架构表述（「单一真源，三层落地」）

```
L0  动作表（desktop_actions.dart）        ← 唯一真源：动作 id ⇄ 名称 ⇄ 路由 ⇄ lh:// path
     │  全模块复用，禁各写一份
     ├─→ L1 寻址契约：统一 URI 形态 lh://<ns>/<key>[/<arg>...]
     │      ns = inbox|todo|journal|ledger|items|habit|today|nfc
     │      ★ 唯一需要「所有外围功能共用」的一层
     │
L2  分发（各路自选，允许不同 action）           ← 不强求统一
     长按菜单/铺到桌面/小组件 → ACTION_VIEW + lh://
     URL Scheme             → ACTION_VIEW + lh://
     NFC 贴卡                → ACTION_NDEF_DISCOVERED(ACTION_VIEW data)  ← 平台定死
     悬浮窗按钮               → 自定义 action + extra（既有，不动）
     App 内 FAB              → 直接调 Dart 函数（零序列化）
     后台 isolate 动作        → service / 自定义 action
     全部汇聚 ↓
L3  Dart 消费：takeLaunchRoute 单次消费  →  同一份去抖/校验/回执实现
```

**收益**：L1 单一真源（行为不分叉）＋ L3 单一消费（校验/去抖/回执只有一份）＋ L2 各按平台语义自由（不跟平台打架）。§6/§7 提的分叉问题在此框架下自动消解。

### 8.5 建议新增条文（并入 V3，**这一组是「地基」，应先于 C36/C37 落地**）

> **C38（新增 · 最高优先）`lh://` 立为寻址契约核心（L1 唯一真源）**：
> ① **URI 形态统一**：`lh://<ns>/<key>[/<arg>…]`，`ns` 全部取自**一张常量表**（与动作表同源生成，禁散落字面量）。
> ② **所有外围功能（快捷方式／铺到桌面／小组件／NFC／未来 URL 入口）必须引用 L1 契约**，**禁**自造 path、禁自定义 action 承载「新功能型」动作（自定义 action **仅**保留给 8.1 那类「后台/悬浮窗、不开 App」的既有链路，**只减不增**）。
> ③ **可扩展性**：新功能一律**加 ns**（如 `nfc`），不进既有 ns；ns 增删需同步改**一处**常量表 ＋ **一处** `handle()` 分支。
> ④ **禁止反向依赖**：外围功能**不得**直接 import 各 feature 的业务方法（守 R1，跨模块一律经动作表/事件总线）。
>
> **C39（新增）分发层不设「统一」KPI（反向裁决，防过度设计）**：
> 分发 action **按各自平台语义选择**，`lh://` 只约束 L1 契约。**明确豁免三类**：
> ① NFC（平台派发 `ACTION_NDEF_DISCOVERED`，App 不可选）；
> ② 不开 App 的后台动作（服务/自定义 action）；
> ③ 既有 `content`/`file` 打开方式（属 EPUB/MD 通路，**禁**并入 `lh` 命名空间）。
> **验收反向**：代码模型若把 NFC 强行改成 `ACTION_VIEW`、或把悬浮窗既有 action 改走 URL、或新造第 4 类自定义 action 承载功能型动作 ⇒ **判越界**。
>
> **B38（新增）契约表须有可测断言**：`test/desktop_actions_test.dart` 增——每个 ns/key 满足「① 形态合规 ② key 唯一 ③ 对应路由真实存在 ④ **解析往返一致**（URI→动作→URI 逐字相等）⑤ 无重复 ns/key」。**禁**只测「id→path 存在」就收工（第 4 条是本条核心）。

### 8.6 落地顺序建议（调整后）

| 序 | 内容 | 说明 |
|---|---|---|
| 0 | 产品点头 C38/C39/B38 | **地基**，改的是「怎么想」不是「加什么」 |
| 1 | C37（桌面四路 Intent 统一）＋ B37 | 桌面侧先定死 |
| 2 | C36（NFC 合流）＋ B35/B36 | 合入同一条解析链 |
| 3 | §2 六条硬漏 H1~H6 | 与寻址层无耦合，可并行 |
| 4 | 软漏 S1~S5 | 收尾 |

**关键提示**：C38 若现在拍板，**H1~H6 的补丁可以照原样并入，不受影响**（那六条都在业务/数据层，与入口契约正交）。C38 不会让前面的评估作废。

### 8.7 一句话结论

**采纳，但改一个字**：不是「以 URL Scheme 为核心」，而是「**以 `lh://` 寻址契约（L1）为唯一真源，分发各随平台**」。
这样既拿到「行为不分叉」的真收益（靠 L1 ＋ L3 单一消费），又不撞 Android 平台语义、也不动 6133/6135 热修承载的真机链路。

## 九、URL Scheme 能力全景 · 功能空间 · 改动面（追加 · 11:08）

> 产品三问：**① 到底能做什么 ② 围绕它能做什么功能 ③ 用它要不要改代码结构**。以下结论均以代码事实为据，**不猜**。

### 9.0 三个决定答案的硬事实（已回查）

| 事实 | 值 | 出处 | 含义 |
|---|---|---|---|
| `scheme="lh"` 注册数 | **0** | `AndroidManifest.xml` grep | **底座尚未注册**——不是「已支持待加强」，是**从零** |
| `GoRoute(` 路由条数 | **114** | `lib/**` 全量 | 可寻址面**极广**，但白名单只列 7 枚 |
| 通知栏动作（`AndroidNotificationAction`） | **0** | `notification_service.dart` | F4-1「通知动作按钮」**完全未开工**，是块空地 |
| `url_launcher` | 已依赖 `^6.3.2` | `pubspec.yaml:66` | **反向唤起**（App 拉其他 App）能力现成 |
| `unknownRouteFallback` | 存在 | `app_router.dart:166` | 未知 path 已有兜底，但会**显示成用户可见页**（见 §9.4） |

### 9.1 第一问：URL Scheme **到底能做什么**

**本质能力只有两条，且都不是「URL」给的，是「外部唤起 + 冷启动路由」给的：**

| 能力 | 说明 | 现状 |
|---|---|---|
| **A. 外部唤起** | 任何外部触发源（快捷方式/小组件/通知按钮/NFC/浏览器/命令行/其他 App）都能拉起本 App 到指定屏 | 需底座 |
| **B. 冷启动直达** | 不经首页、不闪中间页，直接落到目标屏；带参可预填 | 需底座 |
| **C. 无参深链** | 纯路由，不带数据 | 随 A/B |

**它不能做的**（避免误解）：

- ❌ **不能**后台执行（不开 App 就干活）⇒ 须走 service/自定义 action（§8.1 悬浮窗先例）
- ❌ **不能**跨设备（无云同步即无远端唤起，这是本项目现状）
- ❌ **不能**绕过锁屏安全（锁屏态外部唤起受系统限制）
- ❌ **不能**替代 NFC 的**物理贴近**语义（NFC 的价值在「摸一下」，URL 触达不到）
- ❌ **不能**让 iOS/桌面端生效（本项目只做 Android）

### 9.2 第二问：围绕它能做什么功能

按「实现成本 ÷ 收益」排序，**分四档**。注意多数是**已规划但未开工**的，URL Scheme 是它们的**共同底座**，不是新功能。

#### 第 1 档：零新增需求，只是把已定的做对（**必做**）

| 功能 | 现状 | URL Scheme 提供的价值 |
|---|---|---|
| **动态快捷方式 4 枚** | F1-2 未开工 | 统一寻址，一处改动作全端生效 |
| **铺到桌面** | F1-5 未开工 | 同上 |
| **小组件点击** | F1-3 未开工 | §4.4 已明写走 `lh://` |
| **NFC 卡片** | 立项未开工 | 标签里就是 `lh://nfc/<id>` |

#### 第 2 档：**已写进需求但零实现**，URL Scheme 补最后一块（**高性价比**）

| 功能 | 出处 | 缺什么 |
|---|---|---|
| **通知栏/桌面 3 秒记录** | 需求清单模块 5 | `AndroidNotificationAction` 数量 **0** —— 通知按钮点起来**没有底座**；补 URL Scheme 后一行 `payload: lh://...` 即可 |
| **通知动作按钮**（记一笔/打卡/延后） | 桌面方案 F4-1 | 同上，且明确「复用动作表」——**本就打算走 URL** |

#### 第 3 档：**新增功能**（需产品点头，但技术成本低）

| # | 功能 | 形态 | 价值 |
|---|---|---|---|
| P1 | **分享到 LifeHarness**（微信里收到一段文字→`lh://inbox/new`） | 注册 `SEND` 已有通路，只差 path 映射 | 手机上最高频的「记一笔」入口 |
| P2 | **二维码**（把某张 NFC 卡/某个动作印成二维码贴墙上） | 扫一扫走 `lh://nfc/<id>` | **NFC 标签损坏/借出时的降级通道**（§6.2② 已论证） |
| P3 | **自动化入口**（Tasker/Shortcuts/自建脚本调 `lh://…`） | 纯 URL，零开发 | 高级用户玩法，**成本几乎为 0**（底座有了就白送） |
| P4 | **桌面口令/短语**（自定义 `lh://x/<key>` 走用户自建映射） | ⚠ **不建议** | 与动作表唯一真源冲突，见 §9.4 风险② |
| P5 | **URL 内嵌参数**（`lh://ledger/add?amount=38.5&cat=餐饮`） | ⚠ **仅导航类可** | 桌面侧已有 `amount` 先例；**记账类须谨慎**，见 §9.4 风险③ |

#### 第 4 档：**明确不做**（避免无边界扩张）

跨设备远端唤起（需云）、iOS/桌面端、锁屏态行为承诺、后台免开 App 执行（归 service）、自造新 scheme（**只认 `lh://`**）。

### 9.3 第三问：要不要改代码结构

**结论：结构不用改，属「加一层，不改骨架」。** 逐项核对：

| 改动 | 面 | 量级 | 风险 |
|---|---|---|---|
| Manifest 加 `scheme=lh` filter | 1 处 | **2 行** | ⚠ 必须限定 host/path，否则会与既有 5 组 `content/file` filter 抢（§7.2 同一坑） |
| `MainActivity.handle()` 加 `ACTION_VIEW` 分支 | 1 处 | **~15 行**（入队 `pendingLaunch`） | 低。已有 `pendingUri` 模式可照抄 |
| 新增 `lh/launch` MethodChannel | 1 处 | ~20 行 | 低。`lh/intents`（打开方式）、`lh/saf` 已是同一风格，**照既有模式写** |
| `desktop_actions.dart` 动作表 | 1 新文件 | ~80 行 | 低。**唯一真源，后续增量都落这** |
| 路由常量表（ns/key） | 1 新文件 | ~40 行 | 低 |
| `app.dart` 组合根消费 | 1 处 | ~10 行 | ⚠ **必须首帧后**（§6 H2④），否则热修踩过的「无导航状态」类问题重现 |
| 测试 | 新文件 | 3~4 个 | 低。B38 断言 |
| **既有 feature / 路由 / 数据库** | — | **0 改动** | ✅ 走 `context.go(路由字符串)`，**不碰 114 条路由定义** |

**总评**：约 **170 行新增、4 个新文件、既有文件仅 3 处微改**，**零 feature 改动、零 DB 改动**。这与桌面方案 §5.6「不动 DB」、§5.4「禁 feature 直连」的口径一致。

### 9.4 三个必须提前防的风险（否则第一版就会踩）

**风险① 未知 path 变成用户可见的报错页**
`app_router.dart:166` 的 `unknownRouteFallback` 是**页面**。若 `lh://` 白名单未命中就落它，用户点一个失效链接会看到错误页——**与 §6.2② 说的「把内部寻址暴露成用户可见报错」是同一个洞**。
→ **B35 已覆盖**：解析失败/未命中**静默丢弃**（或回今天页），**禁**落 `unknownRouteFallback`。

**风险② 自定义 ns 演化成「用户可编程入口」**
一旦允许「用户自己配 `lh://x/我的动作 → 某屏」`，就等于开了反射式跳转，且要处理参数注入安全问题。**P4 建议不做**；若产品坚持，则必须限定「只能映射到动作表已列条目」，禁自由目标。

**风险③ 带参动作的「静默写错数据」**
`lh://ledger/add?amount=38.5` 若**免确认直接记账**，链接被篡改/转发即产生错误流水。
→ **建议分级**（新增 **C40**）：
- **导航类**（`nav.*`）→ 可带参直接执行（现有 7 枚本就导航类）；
- **写入类**（记账/打卡/计时起停）→ **带参只做预填，提交须 App 内确认**；
- **删除类** → **一律不进 URL**（禁在 URL 里出现删除语义）。

### 9.5 一句话总答

> **URL Scheme 的本质不是「一个链接」，是「本 App 对外暴露的唯一寻址契约」。**
> 它本身不产出新功能，**它的价值是让 8 条已规划/已立项的入口（快捷方式·铺桌面·小组件·通知栏·NFC·分享·扫码·自动化）共用一份底座**——原本每条入口都要自己写一套跳转与校验，统一后只写一次。
> **结构上只需「加一层薄壳」（约 170 行、4 新文件、既有文件 3 处微改），不动 feature、不动 DB、不动 114 条路由。**
> 但要配套三条护栏：**静默兜底（禁落错误页）· ns 不得开放用户自定义 · 写入类带参必须二次确认**。

### 10.5 三条结构性提醒

**① 约 18 条 `:id` 路由不可「直接当 URL 目标」（原写「天然不可 URL 化」，措辞过宽，已修）。**
`/read/book/:id`、`/media/item/:id`、`/ledger/tx/:id`、`/ledger/account/:id`、`/habit/:id`、`/days/detail` 等——**理由是「URL 解析处拿不到 id 的来源」**：这些 id 只在别的模块库/别的屏里产生（涉 R1 跨模块取数），且在**另一台设备上可能根本不存在**。
→ ⚠ **但这不等于「阅读/分类类目标做不了 NFC 卡」**——见 **§10.7**，那是**另一条机制**（id 经**本机卡片表**转译）。**C3/C4 已上调 A 档。**

**② 同一 `lh://` path 可被三处复用，这正是底座的价值。**
例：`lh://habit/check` 同时是——NFC 卡片目标、桌面小组件点击区、快捷方式第 5 枚。**一处改，三处生效。**

**③ 卡片数量建议控制在 6~8 枚。**
超过 8 枚，用户会「摸错卡」——而**摸错卡的代价远大于点错图标**（眼睛会看， 手不会看）。
→ 建议 **A 档 9 条里选 5~6 枚**做卡，其余走小组件/快捷方式。

## 10.7 定级修正：阅读/分类类目标**完全可以**做 NFC 卡（产品指正 · 13:09）

> 产品指正：「阅读为什么不能被 URL 化？写卡时选一本书 → 把 `books.id` 写进标签 → 下次贴一下就带入使用，跟时间分类不是一个过程吗？」
> **判定：产品完全正确，本评估 §10.3/§10.5 的表述有实质错误，现修正如下。**

### 10.7.1 错在哪：我把两件不同的事混成一件

| | **产品设想的机制** | **我误以为的机制** |
|---|---|---|
| 标签里存什么 | **`cardId` 一个编号** | 书的 `books.id` |
| 书的 id 存哪 | **本机 `nfc_cards.target_ref`** | 假设要从 URL 传进来 |
| id 何时解析 | 贴卡时**查本机卡片表**转译出 `books.id` | 以为是「URL 解析处直接拿到」 |
| 跨机是否失效 | **否**（卡片记录跟着备份走，H3/B33） | 是（我误判为失效） |

**「18 条 `:id` 路由不可 URL 化」这句话本身没错**，但它说的是**「这些路由的 id 在 URL 解析处无来源」**（`/media/item/:id`、`/ledger/tx/:id` 这类——外部确实拿不到 itemId/txId）。**我错误地把它推广成了「带 id 的目标做不了 NFC 卡」**，而 NFC 恰恰提供了一条**产生该 id 来源的合法通路**：卡片表。

### 10.7.2 冻结档本来就是这么设计的（证据）

`NFC卡片模块-冻结版开发方案-20261015.md` §2.0 目标表：

| 目标类型 `target_kind` | `target_ref` 取值 | 触发行为 |
|---|---|---|
| `timer.cat` | **`categories.id`**（时间模块分类） | toggle：`activeTiming()?.catId == ref` → `endTiming`，否则 `startTiming` |
| **`read.book`** | **`books.id`**（书架书目） | toggle：`runningSession()?.bookId == ref` → `endSession`＋autoAsk，否则 `startSession` |

**两行结构完全对称**，且 C23 明写「卡片自身**不持久化任何计时态**」，判据**同源读各模块库**。B23 更明确时间卡「只存 `catId` 不存名称」——**阅读卡同理（只存 `bookId`）**，正是「标签只存编号」原则的直接应用。

**⇒ 你的类比精确成立**：写卡时选一本书 → `target_ref = books.id` → 贴卡 → 查 `nfc_cards` 得 `target_ref` → `nfcToggleRead(bookId)` → `startSession`。**与 `timer.cat` 逐字节同构。**

### 10.7.3 修正后的定级

| 项 | 原定级 | 现定级 | 理由 |
|---|---|---|---|
| **C3 阅读卡** | C 档（需带参＋二次确认） | **A 档**（NFC 最佳候选） | 与 `timer.cat` 同构；id 来源合法；零外部传参 |
| **C4 分类计时卡** | C 档 | **A 档** | 同上 |
| C5 `ledger/add?amount=` | C 档 | **C 档（不变）** | 这才是真正的「URL 外部传参」，C40 护栏仍适用 |

**A 档现共 11 条**（原 9 条 + 阅读卡 + 分类计时卡）。若两枚都做，则 §10.6 起步配置里的「⑥ 开始阅读计时 `lh://read/shelf`」应**升级为专属书卡** `read.book`（比进书架再点书少两级跳转）。

### 10.7.4 顺带澄清：为什么「18 条 `:id` 路由不可 URL 化」这话仍然成立

区别在**id 的产生者**：

| 目标 | id 由谁产生 | URL 解析处能否拿到 | 结论 |
|---|---|---|---|
| 分类 / 书目 | **卡片表**（贴卡前已登记） | ✅ 能（查 `nfc_cards`） | **可做** |
| 账目流水 `txId` | 记账模块内部 | ❌ 不能 | 不可做 |
| 影音条目 `itemId` | 影音模块内部 | ❌ 不能 | 不可做（除非新增「扫码/搜索→建卡」入口，**批 3 再议**） |
| 待办/习惯 `id` | 各该模块内部 | ❌ 不能 | 不可做 |

**判据一句话**：**id 必须是「用户可预选并预先登记」的，才配做 NFC 卡。** 书和分类天然满足（用户挑一张贴纸，本来就是挑一个固定对象）；流水和影音条目不满足（那是**运行时才产生的实例**，不是**可预先命名的东西**）。

### 10.7.5 若要把更多目标做进 NFC（批 3 可选 · 需产品点头）

前提是**给目标补一个「可预先登记」的载体**，而非从 URL 硬传 id：

- **待办/习惯卡**：建卡时先从列表选一个**习惯 id**（`/habit/:id` 已有路由）→ 同构可行。价值中等（习惯打卡已由 `habit/check` 覆盖）。
- **影音条目卡**：`/media/item/:id/sessions` 已有路由（该条目的计时明细），建卡时选条目 → 同构可行。**价值较高**（影音游批 3 正在做条目档案）。
- ⚠ 二者都要求**卡片表加 `target_kind` 枚举值**（`habit.item` / `media.item`），属**新增需求**，不在冻结档首批内。

**建议**：首批**只做 `timer.cat` ＋ `read.book`**（产品 V2 已追加的两类），把「可预先登记的目标」这条设计原则写进 §10.8，其余留批 3 按实际需求扩。

### 10.8 建议新增原则（并入 V3 · 由此轮讨论产出）

> **C41（新增）「可预先登记目标」原则（首批目标选择的唯一判据）**：
> 一个目标能配 NFC 卡，**当且仅当其 id 满足「用户可在写卡时预选并写入卡片表」**。
> 首批只配两类（产品 V2 已追加）：`timer.cat`（`categories.id`）／`read.book`（`books.id`）——两者**同构**，仅 id 所属库不同。
> **禁**为满足「URL 化」而从外部硬传 id：那会引入 R1 跨模块取数、跨机失效、参数注入三重问题（参见 C40 分级）。

## 十一、参考 App 调研对照（ZAKER「NFC计时刻怎么用」· 附截图 · 13:13）

> **素材**：用户提供知乎/ZAKER 文章《NFC计时刻怎么用》正文与创建成功后的例子截图。
> **性质**：这是冻结档 C25/C26 提到的「参考 App」的**原始口径**。本节做逐条对照，**只补漏、不推翻已冻结条目**。

### 11.1 它的完整交互流程（原文明写，值得逐字对照）

**空白 NFC 卡的绑定（5 步）**
1. 确认手机支持并开启了 NFC；
2. 打开空白卡写入页面入口：**我的-NFC-右上角-「空白卡写入」按钮**；
3. 将空白 NFC 卡放置手机后，直到**时间日志弹出「写入成功」提示**；
4. **退出空白卡写入页面**，再将空白卡放置手机后识别，**这时候时间日志会自动跳转到 NFC 编辑页**，需要在这个页面为 NFC 命名并绑定一个分类或行为；
5. 创建好后，就可以用该 NFC 卡进行计时了。

**非空白 NFC 卡的绑定（3 步，如门禁卡）**
1. 用任意非空白 NFC 卡放置手机后；
2. 当时**间日志识别到**你的 NFC 卡后，**会自动跳转到 NFC 编辑页**，需要在这个页面为 NFC 命名并绑定一个分类或行为；
3. 创建好后，就可以用该 NFC 卡进行计时了。

**两条高频问答**
- **问：为什么不能息屏刷 NFC 呢？** 答：这好像是安卓的限制，因为手机在息屏情况下识别 NFC 都会有**震动反馈**，说明息屏不会监听 NFC。目前好像还没有什么办法屏蔽。
- **问：NFC 卡片应该选择哪一种呢？** 答：**ntag213 或 ntag215**，外型是硬币大小的圆卡或身份证大小的方卡都行，单价一般在 0.5~2 元。（仅供参考）

**例子截图**（深色态）：顶部栏「× / ? / **空白卡写入**」；下方一行开关「**开启 NFC 计时首选项**」（开启态）；卡片列表左为**彩色标签块**（门禁卡/身份证/社保卡/饭卡），中为**链形连接符**，右为**彩色行为徽标**（学习/工作/洗澡/听书）。

### 11.2 对照结果：3 条实打实的补漏

#### ① ⚠ **它的「首选项开关」语义与我们不同，且我们多一个开关（无争议可采纳）**
它只有**一个**开关：「开启 NFC 计时首选项」——**把 NFC 整个功能的总闸**。
我们 F1-3 的 `/nfc` 屏有**两个**开关（「贴卡行为」两开关，需回查具体两条）。
→ **补 C42**：明确「总闸 ＋ 明细开关」的关系。**建议保留我方双开关**（粒度更细、可单独关掉某一类），但**必须新增一条总闸**，且总闸关闭时：**贴卡无任何反应**（不是报错、不弹提示）——否则用户关了却还有反应，会以为 App 有 bug。
→ 这一点它做得对，我方缺：**开关的「关」必须有可感知证据**，或至少**无反应要静默**（配 §11.4 的震动说明）。

#### ② 🔴 **「写卡」与「绑定」是两步、可分开的 —— 我们方案的衔接可能没写清**
它的流程第 3 步**写卡成功即退出写卡页**，第 4 步**再次贴卡才进编辑页绑定**。
而我们方案是「新建卡片（选目标）并写入标签」**一次做完**（§需求清单「增」＝新建并写入），F2-1 写卡层写成功后**行状态**转「已写入」，随后仍留在弹层里让用户填名称与目标。
→ **不推翻我方流程**（我方一步完成，体验更好），但**补 B39（易踩坑条款）**：
> 写卡成功 → **不要**自动退出/清空弹层；用户很可能「卡已贴好但还没填名称」就去摸手机。
> 若此时系统把该卡当已绑定卡处理（读到 URI → 查表命中 → 触发动作），会在**填名称过程中误触发**。
> **口径**：写卡成功后 3 秒内（覆盖去抖窗口），同一张卡的贴卡**只更新写入态、不执行动作**；弹层保留，等用户完成命名与绑定。
> 判据同源——**以「该卡是否已绑定目标」为准**：`target_ref` 为空 ⇒ 只写库不执行。

#### ③ 🔴 **息屏必然震动 —— 这是它对「为什么息屏不行」给的唯一原因，我们漏了这个用户可感知点**
原文：「手机在息屏情况下识别 NFC 都会有**震动反馈**，说明息屏不会监听 NFC」。
我们 C26 已冻结「锁屏/息屏做不到，不承诺」，**结论一致**，但**只写了边界说明，没写「息屏贴卡会震动却什么都不发生」这个坑**。
→ **补 B40（边界说明必须写成"可感知的事实"）**：
> §5.7 那行锁屏边界文案，**必须点出震动**：「锁屏状态下安卓不派发 NFC 事件（息屏贴卡会震动但不会触发），需解锁后贴卡」。
> 理由：用户看到「震了但没反应」是本模块**最可能的差评来源**。只说「不派发事件」是开发者语言；说「会震动但不会触发」才是用户语言。
> ⚠ 与 C17 呼应：C17 已定「首批不加触觉锚（不主动震）」——**两件事不矛盾**：C17 说的是**我们主动调用**震动马达；这里是**系统在息屏时被动震动**，不可控、也不该屏蔽（原文也明说「目前好像还没有什么办法屏蔽」）。

### 11.3 一条要改的写法（页面设计参考）

我方 §5.7 / F1-3 写的卡片选型灰字是：「NDEF 可写标签 NTAG213/215/216（硬币大小圆卡·单条 URI ≈30 字节，余量充足）」。

它的写法更贴近用户：**「ntag213 或 ntag215，硬币大小圆卡或身份证大小方卡都行，单价 0.5~2 元」**。
→ **补 B41（选型建议按「用户能直接买到」写）**：
> 卡片选型灰字**必含三要素**：**具体型号**（NTAG213/215）＋**外型与尺寸**（硬币圆卡 / 身份证方卡）＋**价格量级**（约 0.5~2 元/张）。
> **不必**在 UI 暴露字节数（那是工程口径，写进工单即可）——**用户要的是「买什么、去哪买、多少钱」**。
> ⚠ NTAG216 可保留在工单里，**UI 首选只列 213/215**（216 更贵更小众，与「好买」相悖）。

### 11.4 列表行设计：一个值得参考的点，但**不建议照搬**

它的卡片行是「**彩色标签块** ─ 链形符 ─ **彩色行为徽标**」——视觉上把「这张卡」和「它触发什么」用一条链连起来，语义表达很直接。
我方 LH-C24 已是「目标类图标 + 名称 + 「目标 · 用过 N 次」+ 写入态」。

→ **补 B42（可采纳的表达，不是照搬配色）**：
> 列表行若目标已绑定，**建议在名称右侧加一枚「目标徽标」**（复用 `LH-K` 系列 chip，**用目标类名**如「学习」「《书名》」），让用户**不用进编辑页就知道这张卡干什么**。
> 这与 C23 的「● 计时中」标记是**两枚独立标记**，可共存（前者＝静态绑定态，后者＝动态进行中）。
> ⚠ **不采纳**它的多色块方案：多色 = 每类一套色，**违背 `UI组件规范.md` 〇B 色值棘轮**，且深浅态要各配一套；我方「图标 + 单色 chip」更省。
