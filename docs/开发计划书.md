# LifeHarness 开发计划书

> 依据：《需求清单 V1.3（冻结版）》｜原型：`prototype/index.html`
> 本计划书定义技术选型、架构、里程碑与排期。需求变更须同步更新本文件。

## 一、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Flutter 3.x（Dart） | 跨端、单代码库、预留 iOS |
| 状态管理 | Riverpod | 编译安全、可测试、依赖注入清晰 |
| 本地数据库 | Isar（首选）/ sqflite（备选） | 高性能 NoSQL、支持复杂查询与全文检索；若生态受限降级 sqflite |
| 图表 | fl_chart | 纯 Dart、PI/柱/线/热力覆盖需求 |
| 本地键值 | shared_preferences | 设置项 |
| 文件/附件 | path_provider、image_picker、file_picker | 图片压缩、导入导出选文件 |
| 通知 | flutter_local_notifications + timezone | 日程/任务/简报/复盘提醒、免打扰 |
| WebDAV | 自建基于 `http` 的轻量客户端（PROPFIND/GET/PUT） | 坚果云应用密码直连，避免重依赖 |
| S3 | 手写 SigV4 轻量客户端（基于 `http` 包；V1.41 引入，不接 AWS SDK） | 缤纷云 virtual-hosted 寻址直连；AWS SDK 已停止支持且丢弃私有字段，SigV4 按规范自实现可控（设计稿 `docs/superpowers/specs/2026-09-24-sync-log-backup-design.md`） |
| 加密存储 | flutter_secure_storage（Android Keystore 保险箱） | 云同步凭据/口令专用存储域（V1.41 拍板：凭据仅手动填入 App、只进保险箱，不进仓库/配置文件/备份导出）；既有 Key 本地化同此机制 |
| 加密 | cryptography（AES-GCM 备份口令加密） | 同步/备份可选加密 |
| 农历 | lunar 或自建转换工具 | 重要日子农历需求 |
| Markdown | flutter_markdown | 笔记渲染/预览 |
| 小工具插件运行时 | webview_flutter + 本地 HTML/JS 工具包规范（plugin.json） | Dart 无法安全动态编译，WebView 沙箱方案可同时支撑「本地目录热加载」与「GitHub 链接下载安装」两种拓展（需求 V1.7） |
| AI 接入 | 无 SDK，Dio 直连 OpenAI 兼容 Chat Completions + flutter_secure_storage 存 Key | 一套协议适配 DeepSeek/Kimi/通义/智谱/OpenAI/Ollama；Key 系统级加密、不随备份/同步导出（需求 V1.8） |
| 公式渲染 | flutter_math_fork（KaTeX 语法） | 笔记 LaTeX 行内/块级公式实时渲染（需求 V1.9） |
| 账单导入 | csv 包 + 自研支付宝/微信表头解析器 + archive（zip 解压） | 两平台导出为 zip 加密 CSV，固定行数元信息前缀，规则解析可离线完成（需求 V1.9） |
| 插件平台（大模块插件化） | 声明式 UI Schema + QuickJS/WebView 双模式沙箱 + SQLite 隔离表空间 plugin_* + GitHub Release index.json/minisign/SHA-256/bsdiff 增量与回滚 | Flutter 不可动态分发 Dart；宿主能力 API + 插件薄层；需求 V1.15 六场景规范；试点：物品/影音游，V1.x 后段 GA |

> 建库策略：V0.1 即定义 待办/日程/日记/笔记 四核心表 **并预留** 健康/财务/物品 表结构与迁移骨架，避免后期数据迁移。

## 二、架构设计

采用分层 + 特性模块化（feature-first）：

```
lib/
├── core/            # 通用能力
│   ├── database/    # Isar 初始化、schema、DAO 基类
│   ├── theme/       # 主题、深色模式、字号
│   ├── router/      # 路由（go_router）
│   ├── notifications/ # 提醒调度
│   ├── sync/        # WebDAV/S3 客户端、备份(.lhbak)/恢复、加密（V1.41 提前实施，口径见设计稿）
│   └── utils/       # 日期/农历/文件大小/哈希去重
├── features/        # 各业务模块，内部 model/data/domain/presentation
│   ├── dashboard/   # 模块6 仪表盘（首页）
│   ├── todo/        # 模块2 待办+四象限
│   ├── calendar/    # 模块1 日程+时间块
│   ├── journal/     # 模块3 日记+笔记
│   ├── reading/     # 模块4 阅读笔记+导入向导
│   ├── inbox/       # 模块5 收集箱
│   ├── finance/     # 模块8 记账
│   ├── items/       # 模块9 物品价值
│   ├── days/        # 模块11 重要日子
│   ├── health/      # 模块12 健康
│   └── settings/    # 通用/同步/外观/关于
├── shared/          # 跨模块联动服务（L1~L14 编排）
│   └── linkage/     # 例：SummaryService, CrossRefService
└── app.dart / main.dart
```

- **联动实现**：模块间不直接互相 import UI，通过 `shared/linkage` 中的服务 + 事件总线（Riverpod Stream/事件）解耦，保证可测试与低耦合。
- **数据流**：Repository 模式，UI ← Riverpod Provider ← Repository ← DAO/DB。

### 2.1 模块解耦规范（2026-09-19 治理定案，守护测试强制执行）

> 目的：防止代码量增长后模块互相牵连——改 A 崩 B、微调引发跨模块回归、测试漏测。
> 可执行化：`test/architecture_test.dart` 每次 `flutter test` 扫描全部 import，违规即红。

**依赖方向铁律**：

| 规则 | 内容 | 违例后果 |
|---|---|---|
| R1 | `features/<A>/**` **禁止** import `features/<B>/**`。跨模块数据/聚合一律经 `shared/linkage/**`（唯一合法聚合层，如 `stats_providers.dart`、`timer_bar_overlay.dart`）；跨模块通知一律经事件总线（`shared/linkage/linkage_events.dart` 定义载荷） | 测试失败 |
| R2 | `core/**` **禁止** import `features/**`。core 只放与业务无关的底座（主题/DB/路由骨架/通用组件） | 测试失败 |
| R3 | feature 的 `domain/`、`data/` 层**禁止** import 任何 `presentation/`——domain/data 是模块对外的稳定契约层（也是未来插件化的迁移边界），必须可脱离 UI 单测 | 测试失败 |
| R4 | 组合根白名单（可装配 feature）：`lib/main.dart`、`lib/app.dart`、`lib/core/providers.dart`、`lib/core/router/app_router.dart`。新增白名单文件必须在本节登记并说明理由 | 测试失败 |

**新模块接入检查单**（写进每个模块 PR 自查）：
1. 目录四分层齐备：`domain/`（模型+仓库）→ `data/`（DAO）→ `presentation/`（页面+widgets+providers），仓库对外只暴露 domain 层；
2. 需要读取其他模块数据？→ 在 `shared/linkage` 建聚合 provider，本模块只 import shared；
3. 需要通知其他模块？→ 定义/发布 linkage 事件，禁止直接 import 对方 provider；
4. 全局 UI（悬浮条/角标类）？→ 放 `shared/linkage/`，由组合根 `app_router` 挂载；
5. 跑 `flutter test`（含架构守护）绿后才可提交。

**每模块测试基线**：domain/data 纯单测（内存库 `databaseFactoryFfi`）+ presentation widget 测试（`databaseFactoryFfiNoIsolate`）+ 联动事件断言（发布/订阅各测一次）。

### 2.2 巨型文件治理规矩（2026-09-29 治理专项定案，守护测试强制执行）

> 背景：G0~G7d⑤ 已把六个巨型文件拆完（reader_page 2834→1108 · shelf_page 2224→547 · sync_sheets 1950→43 ·
> note_edit 1706→312 · read_repository 1955→218 · ai_page 1615→466），schema.dart 1611→392 分九域库。
> 全程事实与手法见 `docs/架构与原型治理评估-20260928.md` §7；各拆分目录内有 README 入口卡。

**体积预算门（`test/size_budget_test.dart`）**：`lib/**` 单文件 **>1200 行**必须先在测试内 budget 表登记
（登记值＝登记时行数），此后**只许减不许增**：超线未登记＝红、长大＝红、变小＝提示收紧、登记项失效＝红。
A 档口径（2026-09-29 用户拍板）：现存 12 个遗留大文件不逐一压缩，长期由此门管住；新文件超线必须先拆。

**再拆任何大文件时的三条路线判据（治理实测定案，勿再试错）**：

| 目标类型 | 路线 | 关键约束 |
|---|---|---|
| 私有巨型 State 类（页面类） | **extension part**（`extension _X on _XState` 移入同库 part） | 字段留类内；extension 内 setState 需逐行定点 `// ignore: invalid_use_of_protected_member`；成员**静态派发**——宿主类加同名成员会静默遮蔽，改前必跑「成员恰好出现一次」双向断言 |
| 公开 API 类（仓储/服务，成员被库外调用） | **同库 mixin + 私有枢纽基类**（`class X extends _XBase with _A, _B`） | extension 成员只在直接 import 声明库时可见，公开类用 extension 会断外联；mixin 禁实例字段；`X(super.db)` 转发构造 |
| 多独立类同文件（弹层库/按类分群页） | **整块 top-level part**（每类自带 State，setState 天然合法） | part 指令必须在任何声明之前（落点＝import 块尾）；块边界「尾吞空行注释 + 头吸紧邻 /// 组」双向修剪 |

**纯移动纪律**：拆分批一律定性「纯移动、零行为改动」，diff 混入逻辑改动即违例回退；每批三门禁＝
`flutter analyze` 零新增（基线 16 issues）+ 受影响域 mini 池全绿 + `bash tools/run_gate.sh` 全量绿；
取证用 `node tools/g7d_puremove_check.js --base <拆前提交> --main <文件> --dir <目录> --parts <a,b>`
（extension/mixin 默认模式；整块 part 加 `--toplevel`；成员与留驻件交错加 `--per-member`；
机械 ignore 行加 `--allow-ignore`）。**取证结果行数=0 必是空断言，不许当通过**。
行为类改进（复审 backlog）一律另立工单，不得混进纯移动批。

**schema 改动规矩**：动 `lib/core/database/schema*` 前后必须跑 `tools/dump_schema.dart` 与
`tools/schema-dump-baseline.json` 逐字段全等（等价性门禁）；新表/迁移按域放入九域库对应文件。

**守护豁免同步**：把带 `aiServiceProvider`/端点 prefs 键的代码外提时，注意 `test/architecture_test.dart`
R7/R8 按 `features/settings/presentation/ai_` 前缀族豁免——新路径必须留在族内或同步改守护；
`kAiCapRows` 是 R8 现场解析锚，**不得挪出 ai_page.dart 主文件**。

### 2.3 日志统一出口与覆盖口径（2026-09-29 真机走查 R14 定案）

> 背景：出口本来就是一套（`AppLog` 环形缓冲 → `FileLogSink` 按天落盘 → 日志页/备份随包），
> 但审计发现**两类偏差**：① 4 处 `debugPrint` 逃逸（release 无痕，已收口）；
> ② 覆盖面空档——11 个 feature 与 3 个 core 子域一条日志都不记（工单见
> `docs/日志覆盖工单-20260929.md`）。

**唯一出口**：业务日志一律 `AppLog.add / addKey / addStack / reportError`。
**禁止** `print` / `debugPrint` / `stderr.writeln` 落业务信息（release 包 logcat 无 Flutter 标签，
真机取证只能靠应用内日志页，逃逸即永久无痕）。

**必须记的四类点**（其余不记，避免噪声挤掉有效信息）：

| 点 | 级别 | 说明 |
|---|---|---|
| domain/data 层 catch 到异常 | warn / error | 带业务上下文（实体 id、参数摘要），不只抛给全局兜底 |
| 外部 I/O（网络/文件/SAF/云）失败与关键成功 | warn / info | 成功走 `addKey`（同步摘要、导入结果、备份落盘等） |
| schema 迁移与数据修复 | info / error | 版本号 + 影响行数，跨设备排查的唯一线索 |
| 跨模块联动事件（linkage）发布/消费异常 | warn | 只记异常与降级，正常路径不记 |

**不记**：UI 层交互（点击/切页/动画）、周期计时器每 tick、可推导的高频量。

**守护（§2.3 的硬拦面）**：`test/catch_log_guard_test.dart` 逐个检查 `lib/**` 的异常处置块（`catch` 与 `on X {…}` 两种形态）是否「有交代」——记日志 / 上交重抛 / `catch-ok: 理由` 批准注释三者之一，新增静默吞噬直接红；存量走登记式棘轮（只许减不许增，清零删项）。写完 catch 不必等评审，跑这一条用例即自证。

**来源标签自动归类**：`AppLog._deriveSrc()` 按调用帧路径映射两级目录（`features/ledger`→记账 等），
新模块只要在 `_srcLabels` 补一行即可进日志页筛选胶囊，**不要手传 src**。

**日志页显示口径（原型 `p-logs` V1.53.4 · R14-11）**：单栏行内流（时间/级别/来源/正文同一段，
不分栏）、**倒序（最新在上）**、堆栈行默认折叠可展开；复制永远全量（含折叠中的堆栈）。

### 3.1 UI 变更确认门（2026-09-19 用户制定，强制流程）

**任何需求调整只要涉及 UI 变动，必须走以下顺序，禁止跳过确认门直接开发：**

1. **先改高保真原型**：`prototype/index.html`（含相关 `prototype/themes/` 配置）实现变更后的视觉与交互；
2. **用户确认**：产品负责人浏览器打开验收（附改动点清单），**获得明确确认**；
3. **需求升版**：确认后同步《需求清单》版本号与变更日志（原型/需求/计划书/交接文档四件套一致）；
4. **进入开发**：Flutter 按已确认原型逐元素保真实现，真机逐屏比对。

原则：**原型是 UI 的唯一事实源**；视觉/交互分歧在低成本阶段（原型）解决，不在高成本阶段（已编码）返工。

### 3.2 原型内置浏览器逐屏走查规程（2026-09-23 用户确认，验收/排障强制走此序）

> 目的：把「打开原型 → 用真实 DOM 与像素定位问题」固化成可复制的动作，任何对话贴本节即可驱动同一套检查。**读代码与静态断言不能替代它**（本轮靠截图抓到三处静态全绿的真实缺陷）。

1. **打开**：用内置浏览器（`browser-use` MCP）`navigate_page` 到 `file:///<仓库>/prototype/<文件>.html`。
2. **切屏切态**：用 `evaluate_script` 调页面自身的路由/渲染函数（如 `navTo('p-habits')`、`hbOpen(id)`、`hbView='grid';renderHabits()`、`openSheet('sheetXxx')`），**每次切换后 `await` 250~500ms** 再取数据（有 transition 与延后渲染）。
3. **DOM 断言**：`evaluate_script` 读真实结构（元素数 / class / title / textContent / scrollHeight），以 JSON 回报。必做一条**文本节点泄漏检测**：遍历目标区域元素的**直接子文本节点**，匹配 `/(^|\s)(ring-|ring-offset|bg-|text-(slate|white|rose|teal|emerald|amber)|dark:)/`——命中即模板把类名写到了 `class` 属性之外（会裸露成页面文字）。
4. **出图核对**：逐屏 `take_screenshot`，看像素、层级、语义配色（例：负向习惯「未触发」是好状态不得标红；触发日必须显性可见）。截图报 `NATIVE_BROWSER_VIEWPORT_UNAVAILABLE` 且 `visibilityState=hidden` = 面板不在前台，**提示用户一次即可，不反复重试**。
5. **控制台**：`list_console_messages` 收尾；除 Tailwind CDN 的 production 警告外应为零错误。
6. **复跑项目校验脚本**：如 `node tools/hbparse.js`（全量解析）、`node tools/hbcheck.js`（emoji + 接线）。⚠️ 这类脚本按注释锚点取区间，**输出出现 `RANGE FAIL` 表示该区间根本没扫，不等于通过**。
7. **闭环**：发现缺陷 → 单点修原型 → 复跑 3~6 → 回报「查到什么 / 改了什么 / 复验结果」；涉及已开发模块的 UI 结论，按 3.1 走确认门再进实现。

## 四、里程碑与排期（V1.16 重排 —— 基于全面评估的单人工时修正）

> 重排原因（评估发现 R-1）：原 V1.0 堆了约 12 个功能簇，单人 6 周容量超载约 40%；且插件平台要求宿主能力 API 在 V0.1 即预埋。现拆为 M0→M4 五段，总量约 29 周；每里程碑含交付物/验收/预案。估算为人工周，CC 协同可压缩处另行标注（通常 20–35%）。

### 7.1 模块预发布流程（2026-09-19 起强制执行，用户制定）

**每完成一个大模块功能**（待办/日程/日记/收集箱/同步等粒度；小修复与保真补丁不算），
在推送 GitHub 分支后，**必须同时创建一个 GitHub 预发布（prerelease）**：

1. **构建 APK（最小体积 · 2026-09-20 用户指令）**：从已提交的模块 HEAD 重新构建，保证发布物与提交一致。
   一律打 **release split-per-abi**（单包约 17~21MB，替代 universal debug 约 147MB，GitHub 下载更快）：
   `powershell -Command "Remove-Item Env:FLUTTER_STORAGE_BASE_URL; flutter build apk --release --split-per-abi"`
2. **命名与附件**：tag `v0.1.0-m0.<版本标记>`；release 资产挂 `app-arm64-v8a-release.apk`（真机主流）+
   `app-x86_64-release.apk`（模拟器）+ `app-armeabi-v7a-release.apk`（老旧 32 位），notes 中标注各包适用设备；
   release 暂用 debug 签名（正式签名随发布工程配置）。仓库 `.gitignore` 已排除 `*.apk`。
3. **创建 release**（含功能描述 + APK 附件）：
   `gh release create <tag> <apk> --prerelease --title "M0 预发布 · <模块>（业务编号）" --notes-file ...`
   notes 固定结构：①本版本内容（对齐原型的保真点清单 + 提交号）②已具备能力 ③已知占位项（后续里程碑）④安装要求（Android 8.0+/minSdk 26/纯本地无账号）。
4. **Gitee 镜像预发布（镜像双推 · 2026-09-25 起成文）**：Gitee 为第一发布通道，GitHub 失败仅提醒。
   `git push gitee <branch>` + `git push gitee <tag>` 后建 release（CLI 无附件能力，只建条目）：
   `gitee release create -R chistoiy/lifeHarness --tag <tag> --prerelease -n <名> -b <正文>`。
   **附件必须另走 API `attach_files` 端点逐包补挂**（实测 201；不是 `upload_file`/`attachers`，均 404）：
   ```bash
   TOK=$("D:/app_workplace/gitee-cli/gitee.exe" auth token | grep -Eo '[A-Za-z0-9_-]{20,}' | head -1)  # token 不落文件
   "…/gitee.exe" api "repos/chistoiy/lifeHarness/releases"   # 查目标 tag 的 numericId
   curl -X POST "https://gitee.com/api/v5/repos/chistoiy/lifeHarness/releases/<numericId>/attach_files?access_token=$TOK" \
        -F name="app-<abi>-release.apk" -F "file=@build/app/outputs/flutter-apk/app-<abi>-release.apk"   # 三包各一次，期望 201
   ```
5. **验证**：**两端** release 的 APK 资产都非空（GitHub `gh release view --json assets`；Gitee `gitee api "repos/…/releases/<id>" | grep -o '"name":"app-[^"]*"'` 三行齐）、tag 指向模块提交；随后删除本地 APK 副本。做 Gitee 操作前先查本条与方案库 `engineering/flutter-android-release.md` R11，不猜端点名。
   - **临时复测包必须与机上已装包同 ABI 形态（2026-09-26 真机踩坑）**：`--split-per-abi` 会把 versionCode 抬成 ABI 前缀形态（arm64=6xxx / armv7=5xxx / x86_64=8xxx），而 universal 单包用 pubspec 原值（如 4024）。已装分包后再发 universal 包安装 → 系统判「无法降级」报 **安装失败(-25)**，处理建议会诱导「卸载重装」（= 清掉真机数据，绝不可从众）。正解：复测包同样 `--split-per-abi` 出对应 ABI，与已装包同 versionCode 即可覆盖安装、数据无损。

首个示例：`v0.1.0-m0.calendar`（日程模块，2026-09-19）。

### 7.2 批次开发两档提速流程（2026-09-21 用户确认，用于多批次版本如 V1.27/V1.28）

> 目标：批内只做增量验证，全套动作集中到收口一次，三批任务从 ~2h 压到 ~70-80min。
> **不削减的门**：UI 原型确认门（§3.1）、R1~R4 架构守护、预发布铁律（§7.1，仅改频率）、测试本身。

**档一 · 批内（每个开发批次结束即做）**：
1. `flutter analyze` + **仅受影响测试文件**（`flutter test --no-pub test/<file> -r expanded`）；跨批无依赖时不跑全量套件。
2. 批 commit（首行详述即可，正文从简；细节靠 git log 承载）。
3. 开发验证期如需真机/模拟器复验，**只构建取证目标 ABI 单包**（模拟器 `--target-platform android-x64` 或 `--split-per-abi` 后仅用 x86_64；真机 arm64），不打三包。

**档二 · 收口（全部批次完成后一次）**：
1. 全量测试套件 + analyze 清零。
2. release split-per-abi **三包构建 + 推送 + prerelease**（按 §7.1，构建可与文档登记并行：先起后台构建再写文档）。
3. 文档登记：需求清单升版 + 计划文档批次对照 + 交接文档状态行/变更日志——**变更日志行压缩到 3~5 行要点+提交号引用**，长流水只留计划文档与 git log。
4. 模拟器取证降为**新交互抽样**：数据正确性/路由/状态已由 widget 测试锁定，真机只截「测试测不了的东西」（动画观感、新弹层布局、首装迁移）；坐标常量（720×1280、底栏 y≈1160、tab 中心 x=72/216/360/504/648）见 `test/helpers.dart` 注释，不再逐屏盲试。
5. 记忆登记（项目级一条：批次交付状态+下一步）。

**测试防坑共享工具（`test/helpers.dart`）**：新用例一律 import，不再各自造轮子——
`settle5(tester)` 5s 限时 settle；`pollText(tester, '文案')` 有界轮询（SnackBar 1.6s 自动消失断言专用，禁 pumpAndSettle 后查 snack）；`useSurface(tester, Size(800, 2400))` 处理懒构建长页（自动 tearDown）。全 app 用例仍**必须拆分独立文件**（isolate 污染教训不变）。

### 7.3 UI 组件规范门（2026-09-21 用户确认）

UI 共同语言固化为 **`docs/UI组件规范.md`**：全部界面元素按 **LH 编号 + 中文术语**登记规格卡（原型锚点 / 代码锚点 / 规格 / 变体 / 可调旋钮 / 使用处）。规则：

1. **指令下达**：产品侧微调按「LH-xx 组件名 调整项」表述（如「LH-S03 添加弹层备注框加高」），开发侧据此直接定位原型 class 与 Flutter 文件，消除描述性歧义。
2. **先登记后开发**：新组件必须先在规范文档建卡（含编号）再进入原型/实现；改原型 UI 必须同步更新对应规格卡——**原型=事实源，规范=索引，代码=实现**三源一致。
3. **原语复用**：通用外观一律走 `lib/shared/widgets/ui_kit.dart`（AppToast / PillChip / DotLegend / MoodRow / SectionCard / EmptyDashRow），禁止页面私调全局组件样式；存量重复调用点按 §7.2 两档流程「路过替换」，不做专项重构批。
4. **令牌边界**：颜色/圆角/阴影等取自 AppTokens（7 套主题 JSON）；「改一处全局生效」类指令优先落在 theme/ui_kit 层。

### 7.4 并行设计会话与开场白交接流程（2026-09-24 用户确认）

模块高保真设计与代码开发在**不同会话并行**进行；交接唯一载体是「仓库文档 + 原型文件 + 开场白」，禁止依赖跨会话复述需求：

1. **设计会话（每模块一个）**：从 `prototype/index.html` 复制 `prototype/index-<模块>.html` 定稿（模块屏只在副本改，共享面由唯一写者 index.html 走变更单回灌，见《多对话原型文件所有权》）。每轮验收按一个 V 修订登记四件套：需求清单（模块段 + 第十节修订记录）、计划书「N·补」节、交接日志行、项目记忆；提交一律**本地不 push**（push 需当次确认）。
2. **开场白（设计会话末件产物）**：设计收口时按固定模板生成开发会话开场白，由用户粘贴给开发会话。模板五段——
   ① **阅读清单（顺序即优先级）**：计划文档主文 + 全部修订补节（明示「与正文冲突以补节为准」）→ 原型文件（声明 N 屏 + M 弹层·UI 唯一事实源·逐屏浏览器比对）→ 需求清单对应模块段与修订记录（注明清单现版号，防止后推进的版本盖住本模块段落）→ 设计规格 → 本文档 §3.2 走查规程 / §7.2 两档提速；
   ② **硬约束**：DB 版本以 `lib/core/database/schema.dart` 实际值顺延（计划中序号仅相对）、模块特有口径（如独立分类树 / 唯一写路径 / 双口径 / 草稿-保存制）、全局 UI 规则（禁 emoji·禁教学文案·就地滚轮）、文件所有权（只动本模块与共享挂载点）、新测试拆独立文件 import test/helpers.dart；
   ③ **节奏**：按计划批次拆解开工，每批交付后做 §逐元素表保真走查再进下一批，逐屏像素验收归产品负责人；
   ④ **push 纪律**：批内 analyze + 受影响测试、收口全量 + 三包 + prerelease、push 前先问；
   ⑤ **未 push 提交链清单**（设计期全部本地提交号）。
3. **开发会话**：按开场白阅读清单执行，不要求用户复述需求；三源冲突时以「需求清单修订记录 > 原型 > 计划文档」为序，先向用户确认再动。
