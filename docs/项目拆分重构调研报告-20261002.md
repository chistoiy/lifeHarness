## 三、代码结构：建议**不**拆仓库/拆 package

### 明确结论：不建议 monorepo、不做 feature package 化

**路线 a（维持单 app 单仓）— 采纳。** 本项目最强的资产是**用可执行测试替代了 package 边界**：`architecture_test.dart` 502 行 R1~R8 八条铁律 + `size_budget_test.dart` 体积棘轮。

**路线 b（每 feature 一个 package）— 不建议**，五条硬理由：
1. **守护当场失效**：`architecture_test.dart:101` 硬编码前缀 `package:lifeharness/`、`:82` 按 `libDir` 相对算路径；拆包后 import 全变 `package:lifeharness_read/...` → `collectImports` 漏采 → **R1/R3/R4/R5 静默空转**。`size_budget_test.dart:34` 同样只扫 `lib/`。**拆包当天就失去唯一的两道门禁。**
2. **零 build 收益**：Flutter/Gradle 不会因 Dart 源码分包减少编译单元；真正的提速来自 R8 拆 apk（见 `docs/APK包体解剖报告-20260927.md`）。
3. **无跨包复用需求**：全库唯一真枢纽是 100 行的 `core/providers.dart` EventBus + 681 行 linkage，远未到需跨包发布的体量。
4. **原型↔实现映射断裂**：`prototype/` 20+ 个 `index-*.html` 与模块一一对应（`index-bookshelf.html`↔read、`index-ledger.html`↔ledger），package 化会打散这个追溯键。
5. **测试重组成本**：198 个平铺测试若按 package 重组，等于在门禁已失效的当下再叠一次大范围移动。

**路线 c（多仓/多 app）— 明确反对。** 单 `applicationId`、单 DB 文件 `lifeharness.db`、34 个版本共享迁移链；跨 app 的 DB 迁移与备份互导（`core/backup/lh_bak.dart` 772 行）无法在编译期保证兼容。**模块下架能力已由架构测试覆盖**（`acdcc29` 删 kits 35 文件 + DB v30 DROP 四表就是先例），不需要用仓库拆分来获得。
