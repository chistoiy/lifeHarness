# 阅读器排版路线说明（2026-10-03）

> 触发＝产品两问：「批三是不是在自研一款渲染器？」「能不能完全自研、全都要具备？」
> 本文＝**路线与硬边界的现行依据**；批三的具体规格仍以 `docs/handoff/交棒话术-20261002-下一版实现批-F01-批C-R32精修.md` §3
> ＋ `docs/预研/原书样式保真CSS画像-20261002.md` §5 为准，本文不重复规格、只定边界与取舍。

## 一、四层拆解：批三动的只是第一层

| # | 层 | 现在谁在做 | 批三是否动 |
|---|---|---|---|
| 1 | **内容层**：EPUB → 段落模型（`EpubPara`：章→段→类型） | 自研 `lib/features/read/data/epub_doc.dart`（archive 解 ZIP＋html/xml 解析） | **动这里**：加一个「很小的 CSS 子集解释器」——读 `<link>`/`<style>`、匹配 class、把声明翻成段落/runs 的属性 |
| 2 | **排版与测量**：一段文字在给定宽度里怎么断行、多高 | **Flutter 文本引擎**（HarfBuzz 整形＋Skia paragraph，经 `TextPainter`） | 不动，也不重写 |
| 3 | **分页策略**：按章懒排、量高切页、分页表落盘、进度定位 | 自研 `EpubPager`/`ReaderLayout`/`PagStore`（借 foliate-js 的模型思路，不是用它的引擎） | 不动，只升指纹/`tableVersion` |
| 4 | **绘制** | Flutter widget 树（`Text`/`TextSpan`，样式统一走 `paraStyle`） | 不动 |

**结论**：批三**不是**自研排版引擎，而是「把原书的排版意图翻译给已有管线」的一层解释器。
说"自研渲染器"只对到第 1 层。

## 二、能力边界（按工程量分档，别混为一谈）

- **周级（批三范围内）**：`color` / `background-color` / `font-size` / `font-weight` / `font-style` /
  `text-indent` / `margin-*`（含 `-webkit-margin-start|end|before|after`）/ `text-align` / `border*`（专名线）。
- **月级**：`<table>`、列表嵌套、图片浮动与图文混排、`column-count` 多栏。难点不在解析，在 Flutter **没有 CSS 盒模型**——
  现在的模型是「一段一个 `TextSpan`」，支持这些要自己写 block/inline 混排与分栏切块，等于把分页引擎重写一遍。
- **年级（硬墙）**：**竖排 `writing-mode: vertical-rl`**。Flutter 文本引擎不支持 vertical writing mode：没有行方向、
  标点不转向、无行首行尾禁则（kinsoku）、无 tate-chū-yoko（竖排中数字/拉丁字母需横排）。要做只能自写竖排排版器
  （逐字摆位＋标点旋转压缩＋禁则表＋数字成组）——**这才是"重造排版引擎"，不是补一层 CSS**。
- **技术上可行但要另定口径**：`@font-face` 随书字体。Flutter 可运行时注册（`FontLoader`），通；
  但 LH-F01 的「不随包字体」指的是**不随 APK**，随书下载是另一件事（体积、首载延迟、缓存清理三件要一起定）。
- **不建议**：SVG、MathML、CSS 动画、媒体查询、完整选择器语义——这些加起来＝重造一个浏览器。

## 三、业界事实核对（别拿"微信阅读全跟了"当目标）

这本《資治通鑑 特殊標點版》原书 CSS 明写 `body{writing-mode:vertical-rl}`（＝竖排），
而**微信阅读同样是横排显示它**，只跟了颜色与字号（见预研 §5.2 第 1 条）。
所以"完全按原书"在业界的实际含义＝**语义样式跟随，版式方向不跟**。把目标定在这一格，
批三就是可达的；把目标定成"像素级复刻"，Flutter 这条路上不可达。

## 四、三条路线与取舍

| 路线 | 原书保真 | 已交付能力（字符级划线·书摘同库·X-Ray·简繁显示层·计时） | 成本 | 适用 |
|---|---|---|---|---|
| **A 自研管线＋CSS 翻译层**（＝批三） | 覆盖"精编本样式写在 class 里"这一大类；竖排/多栏/复杂图文混排不跟 | **全部同源保留** | 周级 | 当前主路线 |
| **B 混合：A＋按需 WebView** | 遇到排版不了的书（竖排本/复杂混排本）时该书整本走 WebView＋foliate-js/Readium 直接吃 CSS | 该书内只读展示，选区/书摘最多做**段级粗锚点** | 中：引 `webview_flutter`＋JS 资产；两套渲染观感不一致；离线与权限单独处理 | "全都要"里性价比最高的一档 |
| **C 换内核：阅读器整体交给 WebView** | 免费拿到全部 CSS 能力 | **全部要跨 JS 边界重做**（选区、CFI 桥、手势、数据库联动） | 高：等于重写阅读器 | 只有当"保真"成为唯一目标时才值 |

V1.50 批1 的选型记录（`epub_doc.dart` 头部）当年否掉 WebView 整页渲染的理由**今天仍然成立**：
与「分页引擎实算＋划词 CFI」路线冲突。

## 五、口径（现在生效，四条）

1. 批三按 A 做完；**不许把 A 一路加厚成"造浏览器"**——超出 §2 周级清单的需求，一律走 §4 的 B/C 重新立项评估。
2. **不静默降级**：解析器遇到不支持的关键声明（`writing-mode` / `column-count` / `float` / `table`）必须
   ① 落日志（一条记录＝落盘一行）② 在该书外观页给一行提示（如「本书含竖排/多栏排版，当前按横排单栏显示」）。
   静默降级的代价是用户以为是我们排错了，而不是"这个格式不支持"。
3. 将来真出现"非竖排不可"的需求 → **单独立项评估 B**，不在 A 上追加实现。
4. 每多支持一项 CSS 语义的固定代价要计入：测量与渲染同源红线需重新保证、`PagStore` 指纹/`tableVersion`
   与 `DocStore.snapVersion` 需升、67 万 span 那本的性能基线会恶化。**这是长期维护债，不是一次性工程量。**

## 六、配套守护（无闸的规矩等于没有）

- **通用性红线**＝实现批必须配源码守护：抽取器源码里出现「按 class 名的字面量映射」即判红，只许出现属性名白名单
  （口径见预研 §5.4，接进 `architecture_test` 族与 `tools/run_gate.sh`）。
- **「不静默降级」可测**：用例断言含竖排/多栏的 fixture 解析后「不支持项」标记非空，且日志里查得到那一行。
- **性能基线**：实现批第一步先量 67 万 span 下的分页耗时，超预算先立性能专项再谈上屏（预研 §5.3）。
