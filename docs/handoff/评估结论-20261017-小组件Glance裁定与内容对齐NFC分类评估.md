# 评估结论 · 小组件 Glance 裁定 ＋「可添加内容」对齐 NFC 建卡分类评估（2026-10-17 立档）

> 来源：产品两问＝①「确认小组件绘制是否使用 Jetpack Glance，必要时重开当前小组件能力，考察下为什么不使用 glance 开发小组件，先裁这个事情」；②「NFC 可添加的事件与小组件可添加的内容完全一致 ⇒ 小组件可添加的内容应以 NFC 建卡页面的分类为准；其中多数内容复用同一套 UI，仅数据不同（例如打卡，均为习惯名称加打卡按钮）；添加小组件时先展示对应的编辑页面以选择对应数据；若为 app 内添加小组件，可直接复用 NFC 建卡页面，但仍需完整展示 UI 样式。评估该方案是否可行，并说明实现思路与潜在风险」。

## 一、Glance 裁定（先裁）

### 1.1 直答：未使用 Jetpack Glance

全仓 `lib/**` 与 `android/**` 对 glance **零命中**；构建脚本无 Compose/Glance 插件与依赖。现行小组件栈＝**原生 AppWidgetProvider ＋ RemoteViews 布局 XML ＋ `home_widget`（^0.10.0）桥**：四枚 provider（今日概览／快捷记账／待办清单／记账概览）＋ 配置 Activity（`android:configure` 落点）＋ 待办行内勾圈原生 Receiver；Dart 侧读数经 `saveWidgetData` 写入插件持有的偏好文件、`updateWidget` 触发重绘，**widget 进程不碰 sqlite**。

### 1.2 「为什么不使用」＝三层事实（不存在「评估后否决」，只有「从未进候选集」）

1. **Glance 从未进过候选集**：2026-10-13 桌面三通道考察件的小组件一行直接写「AppWidgetProvider ＋ RemoteViews（Android 原生）／home_widget（Flutter 桥）」——**没有把 Glance 列为候选、也没有任何对比记载**；此后冻结档、计划书、原型专版、git 提交史对 Glance 全部零提及。技术栈在评估当日即定型为原生栈，随即经批1~3 交付（`lh://` 底座 → 四枚小组件 → 可交互闭环；发行件 6144、复测 6145/6149，真机门已过）。
2. **冻结档口径事实上锁定原生栈**：单一数据桥口径（读数只走 SharedPreferences 快照、widget 进程禁直读 sqlite、**「不引第二套 widget 桥」**）＋ 交互闭环以原生 Receiver 承接。Glance 自带状态与动作回调体系，引它＝换掉 `home_widget` 桥并重写读数架构，**不是换渲染 API 而是换架构**。
3. **已交付资产锁定**：四枚 provider、配置页与布局、Dart↔原生常量交叉守护测试、原型专版屏与其闸，全部围绕 RemoteViews 建；重写＝这些资产连同已过真机门一并归零重立。

### 1.3 逐项对比（「如果换 Glance」会怎样）

| 维度 | 现行原生栈 | 换 Glance 后 |
|---|---|---|
| 渲染写法 | 手写 RemoteViews XML | Compose 声明式，省布局样板 |
| 能力天花板 | 禁滑动、禁文字输入（冻结档判死项） | **相同**——Glance 底层产出仍是 RemoteViews，可滚动容器与文本输入同样不支持，本项目「不做输入控件」的边界不变 |
| 数据桥 | `home_widget` 单桥 | 要么引「第二套桥」违冻结口径，要么以 Glance 机制替换 `home_widget`＝架构重写 |
| 交互闭环 | 原生 Receiver（单列直写＋队列）／批3 计划的后台 isolate | ActionCallback 体系不改变「要跑 Dart 业务就得起 isolate」的事实，无净收益 |
| 主题/深色 | 原生浅/深两档跟随系统 | 略优（可吃应用资源色），但现行口径已冻结且真机门已过，重开要重过 |
| 构建 | 现状 | 新增 Compose 编译器插件与 glance/compose 依赖；本机构建环境对直连下载有 friction（GPU 镜像缺件需换源的既有问题同款），Kotlin 编译校验时长与依赖解析风险上升 |
| 包体 | 基线 | Compose 运行时增量（数 MB 级），与「发行只挂 arm64 瘦身包、禁 ≥100MB」口径摩擦 |

### 1.4 裁定：**维持原生栈，不引 Glance**

理由排序：① 不存在只有 Glance 能 satisfice 的硬需求——能力天花板相同（禁滑动/输入照旧）、交互非它不可不成立；② 切换成本是架构重写而非换皮（桥、状态分发、守护测试、原型闸全废）；③ 已交付且真机门已过的资产不应归零；④ 构建环境与包体口径的额外摩擦。
**重启条件（写明防将来翻旧账）**：若「按桌面实例绑定」方案落地后 provider 与布局数量膨胀（经验阈值 >8 枚）、或交互闭环被迫大规模用 Kotlin 复刻业务规则（行为分叉压不住）——彼时 Glance 的模板化与动作回调收益才盖得过迁移成本，重开评估。

## 二、「小组件内容对齐 NFC 分类」评估（接原问）

### 2.1 事实基线

- **NFC 侧（2026-10-15 冻结、批1/1b/2 已交付）**：目标＝**五段横向大类**（快捷动作〔动作表去掉打卡〕／打卡〔习惯〕／呵护宝宝〔宝宝＋记录类型〕／计时分类〔两级〕／阅读书目）。冻结档原定三区块，批1b 起把带二级选择的目标提升为独立横段，**本评估以现行五段为准**。目标三件套（类／引用／二级参数）落卡片表（DB v49 加三列）；编辑层已有独立「绑定目标」形态（不含卡名与写卡操作），数据源全部走共享挂载层。触发执行 = 贴卡起 App 后 Dart 侧解析执行，同源判据（「计时中」）从各模块库读回。
- **小组件侧（2026-10-13 冻结、批1~3 已交付）**：四枚 provider 各配**全局开关**偏好；配置页＝全局四开关；App 内添加走系统选件对话框＋`requestPinAppWidget`（2026-10-15 产品改口：弃 App 自拼弹窗）；可交互闭环先例＝待办行内勾圈（原生 Receiver 直写单列＋失败队列＋重绘）。

### 2.2 三处前提需修正（先修正，再谈可行）

1. **「可添加内容完全一致」不成立，应改为「动作型一致 ＋ 读数型并列」**。五段里四段（快捷动作／打卡／计时分类／阅读书目）与 widget 动作型完全同构，呵护宝宝可后补；但现有四枚中的「今日概览／待办清单／记账概览」是**读数型，NFC 侧没有「看」的目标**。硬对齐＝砍掉现有能力或造出「快捷动作·今日概览」式的不伦不类形态。建议：读数型保留为并列形态，不进五段表。
2. **「多数内容同一套 UI 仅数据不同」要分层看**。选择层（Flutter）**完全成立**——NFC 编辑层的「绑定目标」独立形态就是现成的五段目标选择器（动作表／习惯／宝宝＋类型／两级分类／书目同一份数据源），widget 添加流以同形态打开即可，这正是产品说的「同一套 UI 不同数据」。渲染层（原生 RemoteViews）**只部分成立**——「标题＋副文案＋主按钮＋状态点」可参数化为共享模板，但每个大类仍要独立 provider 与布局注册（launcher 里一类一条目），且 RemoteViews 禁滚动列表 ⇒ 只能「一枚一目标」，恰好与 NFC「一卡一目标」同构，**是特性不是缺憾**。
3. **「添加时先展示编辑页选数据」受 Android 硬约定约束，须分入口设计**。provider 带 `android:configure` 时，无论从桌面拖动还是 App 内请求固定，都是「pin 确认 → 配置页」，取消则不落桌面。两条入口时序：
   - **App 内入口（贴合产品描述）**：设置页「添加小组件」→ 先开共享选择页（NFC「绑定目标」同款）选数据 → 再 `requestPinAppWidget` → 系统确认 → 配置页读预选绑定无感回写 → 落桌面。用户感知＝**先选后落**。
   - **桌面入口（系统）**：pin 确认 → 配置页承载选择 UI。若要「像 NFC 页」，原生配置 Activity 需转 Flutter 承载（既有 `singleTop` 主 Activity＋方法信道回写先例），多一跳、有可见延迟与主题/返回栈代价，须真机验。

### 2.3 实现思路（分层，从下到上）

1. **目标模型共享层（已就绪大半）**：NFC 的目标三件套＋解析／失效／执行出口收敛为一份「动作目标」服务；widget 与 NFC 共用同一动作表（快捷动作同源，触发结局与 App 内快速记录一致）与同一渲染描述（标题／副文案／按钮文案／图标；「计时中」同源判据照搬）。
2. **选择层（核心改动）**：把 NFC 编辑层目标区抽为**参数化共享组件**（模式参数只影响按钮文案与回调去向；写卡专属分支——探卡、写入状态机、卡号提示——一概不进组件）；App 内添加直接复用；原型沿用 NFC 五段弹层，无需新屏。
3. **绑定层（新增·本方案最关键的新设施）**：从「全局开关」升级为**按桌面实例 id 绑定**——每个 widget 实例绑一条目标。存储建议 SharedPreferences 映射（不动 DB schema、不吃备份/同步复杂度；将来要跨设备同步再升表）。配套：实例删除回收、**老实例无绑定时回落全局默认（升级迁移口径，必须有）**、源数据删除后的失效态定义。
4. **配置页改造**：全局四开关回归设置页（本就同份数据）；配置页只留「本枚绑什么」，并提供「预选绑定无感完成」能力支撑 App 内序。
5. **渲染层**：每类一枚 provider，共享模板复用既有快照下发与深浅色映射；交互按钮的PendingIntent 带实例 id → 新/扩 Receiver。
6. **交互闭环（成色决定点）**：widget 点击不能开 App。原生直写只适合**单列更新类**（待办勾圈先例）；打卡（记录与连击规则）、计时起停（单活域仲裁，先收口再开新段）规则密集，**必须走后台 isolate 跑 Dart**，与 NFC 同出口零分叉（冻结档 §7 原计划路径；现行待办先例是窄例外，不复刻）。

### 2.4 潜在风险（按杀伤力排序）

- **R1 交互闭环行为分叉**（最硬）：计时/打卡若在 Kotlin 侧重写＝双真源，直接违「桌面点一次与 App 内点一次同行为」的既定口径；对策＝写入密集动作一律 isolate 跑 Dart。
- **R2 全局→单实例绑定的迁移兼容**：升级后桌面老实例没有绑定记录，读空即全变占位；必须定义回落与一次性迁移口径，测试覆盖「老实例升级」。
- **R3 配置页承载 Flutter 的可见延迟/黑闪/主题/返回栈**：桌面入口多一跳 Activity；真机门必验「桌面添加」全链。
- **R4 失效态无回执通道**：widget 不像贴卡能起 App 提示，目标被删/被隐藏/快照过期时只能静态占位＋点击引导重绑——需在规格里定义三态文案与去向。
- **R5 多实例快照并发与系统调频**：多实例×单文件快照写、Receiver 与 Dart 对同一库的两条写路径并发；「读数不够实时」是特性不是 bug，口径沿用既有结论。
- **R6 provider 数量膨胀与小米规范**：每个新 provider 都要过名称格式/深色/TalkBack/预览安全区，且拖出列表变长；建议首批只上 2~3 枚动作型。
- **R7 与 NFC 演进耦合**：共享选择器会随 NFC 后续改版（卡复制/带参卡）而动；用模式参数隔离写卡专属分支。
- **R8 门禁成本**：动 `android/**` 必跑 Kotlin 编译校验；新 widget 形态须先过原型门；复测包攒批口径下须产品点名。

### 2.5 建议批次（若立项）

- **批A（验证全链）**：绑定层＋共享选择组件＋App 内「先选后 pin」序＋一枚试点（打卡四格，与 NFC 打卡段完全同构）＋isolate 交互闭环跑通。
- **批B**：计时/快捷动作 provider＋失效三态＋迁移兼容补丁。
- **批C（产品定）**：读数型归并评估、呵护宝宝 widget、配置页承载 Flutter 的必要性复判（若批A 真机发现 App 内序不够）。

## 三、三个追加追问的裁决（同日补·2026-10-17）

**Q1：Glance 对包体有没有影响？** 有，且是结构性增量。以 1.1.0 依赖闭包实证（官方 POM）：除 glance 本体外还拉入 **Compose 运行时＋Compose UI 图形/单位库＋DataStore 偏好＋protobuf-lite＋core-remoteviews**——release/R8 下 dex 合计业界常见读数约 1.5~3MB 量级（精确值须实测量，未测不写死）；本仓 universal 现约 115MB、发版口径只挂 arm64 瘦身包且禁 ≥100MB ⇒ 增量占比不大，但方向上与瘦身口径相悖。另：引 Compose 编译器插件后，本机 6.5 分钟级构建与 3~4 分钟 Kotlin 校验都要变长。**附带结构性冲突**：Glance 官方状态机制基于 DataStore 偏好，与本仓「偏好快照单向下发」是两套存储路径并存，正好踩中冻结档「不引第二套 widget 桥」。**结论：不致命，但零收益的事不加。**

**Q2：按 NFC 方案增加小组件条目，到没到用 Glance 的程度？** 没到，且方案本身与渲染技术解耦。理由：① 规模上限＝五段＋读数并列 ≈ 9 类，首批仅 2~3 类；② 共享「标题＋副文案＋主按钮＋状态点」模板后，每新增一类的原生成本＝一个小 provider 类＋一条信息 XML＋字符串＋清单一项（合计约数十行）——Glance 并不减少 provider 数量（一类一个 widget 子类照样要写），只替代布局写法，而**模板化已拿到这笔收益的大头**；③ 贵的那笔（换桥重写读数架构）与条目数无关，推进多少批都躲不掉；④ 「先选后落」全在 Flutter 侧，RemoteViews 与 Glance 两条路完全一样。**结论：重启条件（provider >8 枚或交互被迫 Kotlin 复刻业务规则）不变，本方案推进不改变该判断。**

**Q3：小组件是不是不具有输入数据的能力？** **桌面上直接打字＝不能，两条技术栈都一样**：RemoteViews 自诞生起不支持任何可编辑控件（放输入框直接渲染失败），也不支持滚动容器；Android 12 起只补了「勾选/单选/开关」这类复合按钮的渲染，仍无输入。Glance 建在 RemoteViews 之上，同样没有。但「不能输入」≠「不能录数据」：① 点击跳 App 内全屏输入是既定铁律（桌面模块原冻结档判死项），快捷记录类小组件本就是这一形态；② 选数据发生在 App 内——本次「先选后落」正是绕开桌面输入的设计；③ 勾选/开关可画成按钮或自绘勾圈（现有待办小组件即是，走的这条路）；④ 近似「桌面弹小窗打字」的唯一路径是点击拉起对话框主题的输入 Activity，本质仍是 App 内页面，且与零输入口径冲突，不采用。**对当前方案无阻塞：打卡/计时/快捷动作全部是「点一下执行」或「先选后落」，没有一个动作需要桌面上打字。**

## 四、交互追加问（Q3 延伸·同日补）：打卡按钮与计数型「±N」是否要打开 App

**结论：两者都可以不打开 App 当场完成；本仓已有同族先例（待办行内勾圈＝点击→后台写→重绘→全程不起 App），但执行出口必须与待办先例不同。**

### 4.1 一条硬事实：打卡不是单列更新

本仓代码实证：习惯打卡执行链＝写一日流水（未来日时钟防护、同日改值不新增、唯一键冲突先清再插、组习惯子项行先删后插）＋**全量重算连击/最佳并回写缓存列**＋水印＋留痕日志。**不能在原生接收器里复刻**（复刻＝行为分叉，且写一半就脏数据）⇒ 必须走**后台 isolate 跑 Dart、走仓库出口**（桌面模块冻结档 §7 原计划路径；现行待办直写是其单列语义的窄例外，明确不复刻）。这也再次坐实评估件 §2.4 R1。

### 4.2 「点击后小组件刷新显示打卡完成」——需补本地回显

现机制：小组件只读偏好快照（App 内下发），后台执行写库后**快照不会自动更新**，重绘读到的仍是旧态——待办现状即「闭环最终一致，显示要等下次 App 推快照才纠正」。方案＝执行成功后由同一路径把**该实例的显示态**写进它自己的快照键再触发重绘（乐观回显），下次 App 推真快照时自然收敛。三态：点击瞬间先乐观回显 → 后台成功 → 快照收敛；后台失败 → 回滚显示态并入待排空队列（App 下次启动补写/纠正）。按实例绑定层天然容纳这类每实例临时态（键带实例 id）。

### 4.3 计数型习惯（默认 30、点一下 ±5、再点打卡带入）——可行，中间值不进库

- **加减按钮**：各带独立点击意图，只改**该实例显示态里的中间计数**（快照键，不动业务库）；「打卡」按钮把中间值一次提交。
- **落点**：单值习惯＝当日流水的数量列；组习惯＝子项数量行（库内已有组/子项结构与当日唯一约束）。提交仍走 4.1 的 isolate 出口。
- **边界口径**：① 中间态只活在小组件实例上，切日/换绑即丢弃，不产生半成品业务数据（不复用库内「自动达成待确认」挂起表，语义不同）；② 提交后小组件只显示「已打卡 · 30」，撤销/改数回 App 内（与 NFC「复杂编辑回 App」同口径，初期不做小组件内撤销）；③ 带参执行口径：NFC/小组件已按产品口径放宽为直执行，计数「±5 再提交」本身就是本地确认形态，规格里写明即可；④ 每枚按钮须配读屏标签（小米规范）；⑤ isolate 冷启动几百 ms~1s+ 的延迟由乐观回显盖住；点击走广播直达不经系统调频，响应可靠。

### 4.4 对方案的影响

不改 §2.3 分层结论，仅让批A 试点更饱满：打卡四格试点即含两种交互形态——「点击打卡→本地回显→后台 isolate 提交」与「计数型 ±N→一次提交」。若真机 isolate 冷启动延迟不可接受，降级路径＝待办式待排空队列（显示态同样回显，写入最终一致）。

## 五、参考实现拆解（一叶日记 me.liujia95.solitude · 2026-10-17 真机拉包解析）

### 5.1 一个横贯全文的事实：用 Compose 做界面的 App，小组件也没用 Glance

该 App 无 Flutter 引擎（原生库仅 mmkv/友盟）、屏内有 Compose 布局（统计页），**五枚小组件全部原生 AppWidgetProvider＋RemoteViews**。这是 §1.4 裁定的业界旁证：连重 Compose 的团队都在小组件上用 RemoteViews——Glance 不是默认答案。

### 5.3 可借鉴点（按本仓映射）

1. **实例级配置是标准做法**：它的 configure 按 widgetId 存选择（哪个分类/哪些分类/哪个象限/哪个计划）＝本仓 §2.3 绑定层的同构先行者，且没有全局开关——印证「全局偏好→单实例绑定」方向正确。
2. **同一功能两枚两粒度**：计时拆「单分类/多分类」两枚。映射：打卡段可做「单习惯打卡格」（与 NFC 打卡卡同构）＋「今日打卡片区」（读数型·NFC 没有的并列形态）两枚。
3. **label 命名＝功能-形态**（计时-单分类/计时-多分类/待办项-四象限）：用户在桌面添加列表里选得清；本仓四枚的「今日概览/快捷记账」类命名可改此口径。
4. **失效两态而非单占位**：占位布局文案即「获取数据失败」（另有「未选择/无数据」态由配置缺失触发）——本仓规格需定义三态（无快照/无绑定/源失效），现为单占位。
5. **网格＝手工嵌套线性布局**（预览里的彩色网格在布局 XML 里是横竖嵌套线性布局拼的）——坐实「标题＋主按钮」模板就是 RemoteViews 的可行形态上限，§2.2 判断重申。
6. **交互闭环完成度更高**：它的多分类网格「点分类即起停计时」（不起 App）；本仓计时/打卡 widget 的点击闭环可对标此完成度（执行通道仍须 isolate· §4.1 不变；其 dex 加固读不到实现，仅作目标参考）。
7. **280×80 横条形**是本项目没有的实用尺寸（4×1 横条读数）——「今日打卡进度 4×1 横条」可作为读数型并列形态候选。
8. **URL Scheme 双轨**：固定 scheme `sjrz://api/...`＋**用户可自定义 scheme 的编辑页**（透明 trampoline Activity·noHistory/excludeFromRecents）＋NFC 外部类型记录——与本仓 `lh://` 同思路，「允许用户自定义触发链接」是可借鉴产品功能。
9. **MMKV 做轻量存储**；provider 未设 `description` 字段（介绍由 label 承载）。

### 5.4 对批A 的直接影响

① 试点命名改「功能-形态」口径（如「打卡-单习惯」）；② 占位/失效三态进规格；③ 「今日打卡进度横条」读数型列为候选（不入 NFC 五段，正属并列形态）；④ 「大类切换行」交互可作计时多分类 widget 的借鉴；⑤ 其执行通道不可读，不改变「互动闭环走 isolate」的本仓结论。

### 5.5 更深一层为什么读不到（反编译工具路径已走完·留档防翻旧账）

产品问「REA 这类逆向工程项目也没辙吗」——已实测到字节级结论：**静态路全部走到头**。证据链：① classes.dex 头部声明长度＝文件实际长度（无尾挂加密体）；全包 1896 项扫描无第二个 dex magic、无 zip-in-zip；>100KB 文件逐项熵判无异常件 ⇒ **原 dex 根本不在包里**；② classes.dex 6.19MB 但 app 自有类引用 0、kotlin 引用 0 ＝壳加载器桩；assets 内 `.jgapp` 标记＋五枚 libjiagu ＝ 360 加固（运行时/云解密型）；③ REA（NabilRFG12/morluto·npm `rea-agents`）的 Android 能力经其源码逐字证实＝**未修改的 jadx-headless-mcp 0.7.1 JAR**（class 注释原文）＋ apktool（仅资源），无任何脱壳逻辑 ⇒ JADX 读壳桩，REA 同样。本机 GitHub release 资产被墙（JADX 未跑成，结论由上述证据锁定不依赖工具运行）。**只剩动态脱壳**（内存 dump／虚拟容器类工具或 Frida dexdump）：都要设备在线，前者 Android 12 封顶（该机 Android 16），后者多半要 root；设备锁屏即断已试重连失败。已拿到的（清单/信息 XML/布局/预览/广播动作/配置模式）对批 A 够用，执行层拿不到不影响本仓结论。
