## 1. P0 结论（三条）

### F1 · 包内附件与日志「只进不出」——恢复只还原 DB，不落盘附件

**现象**：导出时 `attachments/note_images/**`、`attachments/book_covers/**`、`attachments/exports/**`、`logs/**` 都进包；**恢复时一个文件都不落盘**，只做整库替换。

**证据**
- `lib/core/backup/lh_bak.dart` 416 行注释自陈：`附件/日志的落盘恢复属导入 UI 任务（T10），此处只恢复 DB`；
- `BackupService.importBackup`（`lib/core/backup/backup_service.dart` 317~389 行）顺序＝verify → 恢复前自动备份 → close → `unpack` → reopen → 报告，**全链无附件解包**；
- 全仓检索 `attachments/` 只命中**打包侧**（`lh_bak.dart` 707／714 行）与同步侧映射（`snapshot_service.dart`），**无任何恢复侧落盘代码**。

**影响（严重度高于表面）**
- 恢复后 `note_images/` 空目录，而 DB 里日记/笔记/健康症状照片/PDF 报告的路径行齐全 ⇒ 正文图片全部悬空、图集页全空；
- 「换机恢复」正是该功能的主用途，而它恰好是附件全丢的场景；
- 唯一兜底＝恢复后重新配置云同步、由文件级差异把 `note_images/book_covers` 拉回来——但**恢复期不改 prefs（见 F13）**，换机后云配置本身也丢了，兜底不成立。

**口径现状**：设计稿与需求清单**两处均未表态**「附件要不要还原」（既没承诺也没否决，无 TODO 标记）＝口径空白，须产品裁定。

**可选修法（两条，择一）**
1. 补齐：`unpack` 增加附件/日志解包落盘（成员名 `attachments/<目录名>/<相对路径>` 反查回 `attachDirs`；根层散文件回根目录；`logs/` 回日志目录），恢复报告增列「附件 N 项 / 日志 N 个」；
2. 明示：不做落盘，则校验卡与恢复确认必须写清「附件不入恢复」，避免用户以为图也跟着回来了。

### F2 · 恢复低版本包 ⇒ schema 漂移且迁移永不触发

**现象**：包 `dbVersion < 当前` 一律放行；恢复后表按**旧包 DDL** 重建（只补「整表缺失」的空表，不补列），而库的 `PRAGMA user_version` 仍停在当前值 ⇒ 之后每次开库都判「已是最新」，`onUpgrade` 永不触发。

**证据**
- `lib/core/backup/lh_bak.dart` 360 行：只拒 `dbVersion > DbSchema.version`（`versionMismatch`），旧包放行；
- `unpack`（417~481 行）：`DROP` 目标表 → 按快照 `sqlite_master` 重建 → 逐表 `INSERT` → 重建索引/触发器；缺失**整表**建空表，**不含列级补齐**；
- 全仓 `grep user_version` → **lib 侧零写点**（只有测试手工钉 `PRAGMA user_version`）；`AppDatabase.open` 靠 `openDatabase(version: DbSchema.version)` 的 user_version 比对触发迁移（`lib/core/database/app_database.dart` 41~64 行）。

**影响**：恢复 v39~v43 时代包（本机 `exports/`、`backup/` 与云端存量包都有）后，`journal_entries.deleted_at`（v44）、`notes.wb_at`（v43）等新列不存在 ⇒ 日记/笔记查询 `no such column` ⇒ 功能瘫痪且**自愈路径为零**。同族风险在 `docs/STATUS.md` 已记过（6109 漏改 version 导致真机日记读写全断），此处是同一根因的另一条入口。

**修法建议**：恢复成功后按 `manifest.dbVersion → DbSchema.version` 复用 `DbSchema.migrations` 逐级补齐（迁移语句必须幂等，或用列存在性判定）；或产品裁定「只允许恢复与当前版本一致的包」（口径变更，需明说）。**无论选哪条，都要补一例「退版包恢复」常驻用例**（同族守护 S6/S7 口径）。

### F3 · 备份包会内嵌其它备份包（`exports/` 整目录无扩展名过滤）

**现象**：`attachDirs` 含 `<docs>/exports`，而该目录正是**云同步下载 `.lhbak` 的落点**；打包侧对 `attachDirs` 递归收**全部文件**、无扩展名白名单 ⇒ 每次导出都把历史下载包再包一层。

**证据**：`lib/main.dart` 197~203 行（`attachDirs`＝note_images／book_covers／exports）＋`lib/core/sync/sync_orchestrator.dart` 429／448 行（下载落 `exportsDir`，`BackupFileScanner.markDownloaded` 记名）＋`lh_bak.dart` 695~709 行（`listSync(recursive: true).whereType<File>()`，无扩展名筛）。根目录浅扫的白名单 `kRootAttachExts` 只作用于 `attachRootDirs`，**管不到这里**。

**影响**：包体积随下载历史虚增（包内套一枚 40 MB 的下载包 ⇒ 导出包 +40 MB）；加密档只在单文件 >64 MB 时跳过（`skippedLarge`），拦不住 15~40 MB 的 `.lhbak`；用户在 DB 概览看到的「备份包体积」也会被自己撑大。

**修法建议**：收 `exports/` 时排除 `.lhbak`（或统一改成扩展名白名单口径），并在导出前把「排除 N 个备份包」写进日志/包信息。

## 3. P2 结论（存储、保留与能力延伸）

- **F10 · 本机包无保留策略**：同步目录有 `keepN` 裁剪（`snapshot_service.dart` 313 行起），而 `<docs>/backup/`（本机导出＋`auto_before_restore_*`）与 `<docs>/exports/`（云下载）**只增不减**；每做一次恢复必新增一枚（20~90 MB 量级），清理由 B-1 手动删。建议：给 `auto_before_restore_*` 设上限（如保最近 3 枚）、在备份文件屏与 DB 概览出「可释放 X MB」读数。
- **F11 · B-1 屏能力偏薄**（原型亦无，属新增面，须先改原型过门）：包详情（含哪些表/附件）、**另存到/分享**（把包交给文件管理器或发给别人——包是「带走数据」的载体，当前屏内没有任何出口）、上传到云端、按来源筛选/排序、顶部「上次备份距今多久」。
- **F12 · 入口语义重叠**：`/sync` 主页同时挂「备份导出/导入」与「备份文件」两行，两处都能触发恢复；前者是「造包/选外部包」，后者是「管理本机包」，用户不易区分。
- **F14 · 无备份健康度提示**：没有任何「距上次成功备份 N 天」的提醒；配合「定时/自动本机备份无需求条目」（设计稿只声明了同步目录的 keepN 裁剪与迁移前备份），用户对「我到底有没有备份」无感知。
- **F15 · 口令 UX 与救援文案**：口令框无明示/隐藏切换（`obscureText` 固定）、无强度提示、无「口令丢失＝包无法恢复」警示；恢复侧口令错误也只回 `wrongPassphrase`（并入 F7 一起改）。
- **F16 · 第二套备份入口并存**：阅读 X-Ray 词库另有独立导出/恢复通道（`lib/features/read/data/xray/xray_backup.dart`，按册 MD5 校验），与整库备份语义不同但用户视角像两个「备份」；无需合并，但建议入口文案区分开。

## 4. 做对的部分（避免误伤，一并记录）

- 前置校验失败时**现库一字节不动**；`unpack` 全程单事务＋`PRAGMA defer_foreign_keys`，失败回滚并**经注入的 `closeDb` 重开**（裸 `Database.close` 会留缓存死句柄的老坑已修＋有回归用例）。
- 快照走 `VACUUM INTO`（不拷活文件）；同秒重名 `uniqueFileNameInDir` 去重**绝不覆盖**已成包。
- 校验和值编码长度前缀化（NULL 与字符串 `'NULL'` 不再同串）；KDF 算法白名单＋轮数封顶区间，坏 manifest 不能拿 10^9 轮拖死解侧。
- 可再生三表（`xray_mention`/`xray_entity`/`xray_task`）恒不进包，真机实测体积/校验量砍约 97%。
- 恢复前自动备份**只落本机导出目录、永不进同步目录**（设计红线守住）。
- B-1：来源三档角标、删除＝物理删＋二次确认（含「auto 档＝回滚资产」单列警示）、`purge` 越界拒删护栏、进屏重扫（F-8/F-9 已修）、空态与批量态照原型。
- 健康「随本地备份」开关（`healthExcluded`）与同步侧的 `careExcluded` **反向兜底**（本地侧读失败按「含进包」、云侧按「不外传」），两害不同级的判断写在了注释里。

## 5. 测试覆盖的空白（与上表对应）

1. **附件侧零断言**：现有用例只断言 `members` 里有附件、`skippedLarge` 有记录，**没有一例断言恢复后目标附件目录真的有文件**（因为功能不存在）。
2. **跨版本恢复零断言**：`backup_restore_test.dart` 只测「包版本 > 当前 ⇒ 拒」；「包版本 < 当前 ⇒ 恢复后 schema 是否可用」无例（F2 的守护应落在这儿）。
3. **恢复后界面态零断言**：无「恢复完成 ⇒ 数据刷新/导航」的用例（F4）。
4. 另建议补：`auto_before_restore` 命名与保留策略用例、`exports/` 收包排除 `.lhbak` 用例（F3）。

---

## 6. 建议的处置顺序（不动手，等产品裁）

1. **先定三条口径**（P0，定完才是实现批）：① 附件/日志是否随恢复落盘；② 低版本包是「迁移补齐」还是「拒收」；③ `exports/` 收包是否排除 `.lhbak`。
2. **一批做完 P1**（可合批，改动集中在 `sync_backup_sheet.dart`＋`importBackup` 返回面）：F4 恢复后刷新/导航 → F5 恢复报告卡 → F6 恢复中锁层与进度 → F7 人话错误 → F8/F9 校验卡与确认行补项。
3. **P2 攒下一批**：F10 保留策略、F11 包详情与「另存到/分享」、F12 入口语义、F13 prefs 口径分离、F14 备份健康度提示。
4. 上述 1~2 若进实现，UI 侧按铁律先改原型过门（P1 的 F4/F5/F6/F8/F9 都是看得见的面）。
