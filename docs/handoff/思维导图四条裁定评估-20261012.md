# 思维导图·四条产品裁定评估（2026-10-12）

> 口径：产品 2026-10-12 就功能排查件的三条待裁 ＋ HTML 导出可行性，四条逐条评估回源。
> 结论先行：**四条全部可行**。HTML 导出**技术上零阻力**（项目已有 SAF 另存通道 ＋ 写文本文件 ＋ `webview_flutter` 依赖），
> 且它比 .xmind 更该做 —— 补掉了「只能看不能编辑」的缺口，代价只有几百行。
> 横屏那条约得对：**预览横屏**比**编辑横屏**划算得多，且和「布局形态双向延伸」是同一件事的两面。

## 一、导出「可操作的 HTML 文件」——可行，且建议列为独立出口

### 1.1 可行性回源（三处基建全在，零新增通道）

| 需求 | 项目现状 | 落点 |
|---|---|---|
| 生成文本文件 | ✅ `lib/core/platform/open_intent.dart:66` 已 `f.writeAsString(content)` | 导图 HTML 模板直接拼串 |
| 另存到用户自选位置 | ✅ `lib/core/platform/saf.dart` 的 `safSaveAs(srcPath, fileName)`（`lh/saf` 自研通道，走系统「创建文档」） | 落临时文件 → `safSaveAs` |
| 在 App 内预览这份 HTML | ✅ `webview_flutter` 已在 `pubspec`（豆瓣登录页在用），`MainActivity.kt` 已有 `ACTION_VIEW` 处理 | 预览＝导图页一个「预览」入口 |

**结论：不需要任何新增原生通道，纯 Dart 侧即可落。** 这比 .xmind（zip 解包 + JSON 多版本 schema 兼容）便宜一个量级。

### 1.2 为什么这个出口值得做

你提这条的直觉是对的，理由有三条：

1. **补上「可操作」的缺口**。PNG 是死的、md 是大纲、XMind 要装软件。HTML 是**双击就能在浏览器里看、能折叠、能点开挂载笔记标题**的 —— 恰好是这个模块最需要的「给别人看」形态。
2. **和「零云依赖」的产品定位天然合**。项目全程离线优先、不做账号体系，HTML 导出让「分享」这件事**不需要服务器**，比「公开链接分享」那条（排查件里建议砍的）轻得多 —— 我把那条改成「HTML 导出可分享」，砍法调整。
3. **它是 `.xmind` 导入的天然对偶**。先做 HTML 出口能验证「导图序列化层」是否设计干净（节点/边/坐标/挂载引用四类数据能否无损表达），这个验证对将来做 .xmind 有用。

### 1.3 建议的 HTML 导出规格（须你确认四点）

- **单文件、零外链**：CSS 与 JS 内联，**不引 CDN、不引外部字体**（与全项目「不随包字体文件」口径一致）。双击即用，断网可用。
- **可操作三件**：折叠/展开节点、节点点击跳**挂载笔记的标题与摘要**（导出时把笔记标题快照进去）、画布平移缩放。**不含编辑**（HTML 里不做编辑器，那是另一个数量级）。
- **与 App 内视觉同源**：用同样的纵向树布局算法生成初始坐标，深浅色跟随系统 `prefers-color-scheme`（导出文件内联两套令牌，零请求）。
- **挂载隐私口径**：节点挂了笔记时，**默认只导出笔记标题，不导出正文**。要正文得用户在导出弹层单独勾（默认关）。这是私密数据，日记/笔记内容不进一个可能被随手转发的文件。

### 1.4 代价与排期

约 300~400 行 Dart（模板拼串 ＋ 折叠 JS ＋ 两种色档令牌）＋ 复用现有 PNG 的导出弹层骨架。**建议并入批 2**，和 md/opml 导出同批做（同一套序列化层，分三个渲染器）。

## 二、布局形态：两套都做 ＋ 左右双向延伸

### 2.1 裁定落定

「两种都做」+「左右双向延伸」= 实际是 **4 种形态**，建议按 `LayoutEngine` 接口实现，切成两个正交维度：

| 维度 | 取值 | 说明 |
|---|---|---|
| **结构** | `tree`（纵向树）｜`radial`（放射） | 放射＝中心节点在中间、四周发散，MVP 清单要求的「默认放射状」 |
| **方向** | `right`（向右延伸）｜`both`（左右双向） | `both`＝子节点按数量均分到父节点左右两侧，奇数时右侧多一个 |

**默认口径建议**：新图默认 `tree` ＋ `right`（竖屏可读性最好，就是现在原型这形态）；用户在画布工具条一键切 `both`（左右铺开后横向空间利用率翻倍，正好解决长树挤成一条线的问题）。

### 2.2 一个必须提前说的技术后果

左右双向延伸对**数据模型**有影响，现在就得记下来，否则批 4 做时会推翻批 1：

- **父节点不再持有子序**。`both` 模式下「第一个子节点」不存在，只有「子节点集合 ＋ 每个子节点有 `side: 'l' | 'r'`」。
- **`side` 必须是节点属性、可为空**。为空 = 未指定，由布局引擎按索引自动分配（首次 `tree/right` 时全空，用户切 `both` 时自动分配，写回 `side`）。这样 `both` 退出时能恢复。
- **拖拽偏移 `dx/dy` 与 `side` 正交**：现有口径（只存相对基线的偏移）继续成立，切 `both` 时偏移直接复用。这是上一轮定「不存绝对坐标」的额外收益 —— 现在看那个决定是对的。

### 2.3 排期

- **批 1** 先把 `LayoutEngine` 抽象接口立起来（只有一个 `tree/right` 实现也算），**不要等批 4 再抽** —— 批 4 才发现要抽接口，等于批 1 到批 4 的渲染代码全要重写。这是本次四条裁定里最需要前置的一条（和「大图性能」同类）。
- **批 4** 加 `radial` 与 `both` 两个实现 ＋ 工具条切换入口。

## 三、大导图性能：确认前置，写进批 1 的硬要求

你判「前置，避免后期整改成本过高」——完全同意，而且这是四条里**技术风险最高**的一条。把可执行的规格先定下来：

### 3.1 渲染层口径（批 1 必须落地，否则批 5 加样式时必推翻）

| 项 | 规格 | 不这么做的后果 |
|---|---|---|
| **画布渲染** | 节点与连线走 **`CustomPainter` ＋ 单个 `RepaintBoundary`**，不进 Widget 树 | 每节点一个 `Widget` ⇒ 千节点即千次布局，实测必卡 |
| **可视区裁剪** | 维护 `viewport`（当前平移/缩放/屏幕矩形），**只绘制与可视区相交**的节点与边 | 全量绘制 ⇒ 节点数线性增长，缩放时必掉帧 |
| **文本** | 节点标题测量走 `TextPainter` 并**缓存量宽**（改文字才重算），不要每次 `Text` Widget | 每帧重排文字是 Flutter 画布卡顿第一杀手 |
| **拖拽降级** | 拖拽中**只重画当前节点与其邻边**（局部脏区），松手后再整树重排 | 拖拽时整树重绘 ⇒ 上千节点直接掉到个位数帧率 |
| **连线** | 折线批量进同一个 `Canvas.drawPath`（或 `drawVertices`），不要每条边一个 draw call | 边数是节点数的 n 倍，逐条 draw 放大成本 |
| **节流** | 平移/缩放手势帧内只更新 `Transform`，布局计算延到帧末或节流 | 每帧重算布局 ⇒ 布局成为瓶颈 |

### 3.2 数据层配套（批 1 一并定）

- 节点表**按 `map_id` 索引**（`(map_id, parent_id)` 复合索引），拉整图时不扫全表。
- **子节点顺序**用一个 `sort` 整数字段，不靠 `rowid` 隐式序（`both` 模式要重排，右移/左移都得改序）。
- **是否需要扁平表**：建议**是**。用 `(map_id, parent_id, side, sort)` 存扁平节点，不做邻接表 JOIN —— 单机 SQLite 上扁平表读整图快一个量级，且省掉一层递归查询。

### 3.3 验收线（建议写进批 1 的真机门）

- **1000 节点**的图：打开 ≤1.5s，平移/缩放**稳定 ≥50fps**，内存不随平移增长（可视区裁剪生效的读数证据）。
- 5000 节点：打开 ≤5s，交互 ≥30fps（达不到也要保证「能用」而非「流畅」）。
- 断言口径：**不许用 50 节点的测试数据推断性能**，真机门必须在真机真数据上跑。

## 四、横屏：只做「预览横屏」，不做编辑横屏

### 4.1 你的方案可行，且建议把范围写死

「预览时横屏」= **把已画好的导图按横向重排一次给人看**，不做横屏下的编辑。这个界定非常关键，它让成本从「动全局 `app.dart` 接横屏」降到「画布内一次布局切换」：

| 项 | 全项目 grep 结果 | 结论 |
|---|---|---|
| 全局 `Orientation` 监听 | ❌ **零命中** | 接横屏＝动 `app.dart` 全局，要动所有页面 |
| 画布容器尺寸自适应 | ✅ 画布是 `LayoutBuilder` ＋ 自己算 `viewport` | 换个 viewport 重算即可，与横竖屏无关 |

**所以「预览横屏」在实现上就是「把 viewport 尺寸临时换成宽屏比例 ＋ 重排 ＋ 退出预览还原」**，不碰系统方向、不碰全局布局。

### 4.2 但有个前提要说清

**在手机上强制横屏预览，用户往往没法把手机横过来看**（除非支持旋转跟随）。所以「预览横屏」有三种落法，价值差很多：

| 落法 | 用户体感 | 成本 | 建议 |
|---|---|---|---|
| A. 强制 App 转横屏（预览时改 `SystemChrome.setPreferredOrientations`） | 手机得跟着转 | 中（碰全局通道，退出要还原，有还原失败风险） | **不建议**，动全局且有状态残留风险 |
| B. **不转屏，只把画布在竖屏内转成横向比例**（宽画布用双指缩放看） | 手机不用转，但画面是「缩小的横向图」 | **低**（纯画布内布局，不碰全局） | ✅ **建议这个** —— 实质是「横向布局预览」而非「横屏」 |
| C. 导出 HTML 里的横向布局 ＋ 系统浏览器打开 | 系统浏览器能转屏，交互免费 | 零（并入 HTML 导出） | ✅ **建议一并做** |

**我的建议：做 B ＋ C，放弃 A。** B 满足「在 App 内看横向布局」，C 满足「真正横屏看」（交给浏览器，用户想转就转）。这样既回应了你的诉求，又完全绕开了全局横屏改造。

命名上建议叫「**横向布局预览**」而不是「横屏预览」，避免用户误解成转屏能力。

### 4.3 与布局形态的关系

这一条和第二节是同一件事：**方向维度 `right` / `both` ＋ 布局形态 `tree` / `radial`，在横宽 viewport 下的表现，就是「横向布局预览」**。所以它不该是独立功能，而应是**「布局切换」家族里的一个预设**：

```
布局预设 = 结构(tree/radial) × 方向(right/both) × 容器比例(竖屏友好/横向预览)
```

批 1 只要把 `viewport` 与布局解耦（本来就该解耦），批 4 加这套预设就是水到渠成，不用返工。

## 六、要你再确认的两点（✅ 2026-10-12 产品已确认）

1. ✅ **HTML 导出的挂载隐私口径已确认**：节点挂了笔记时，默认**只导标题不导正文**；正文需用户在导出弹层**单独勾选（默认关）**才带。日记/笔记正文不进一个可能被随手转发的 HTML —— 此口径为**硬口径**，实现批不得提供「默认带正文」的开关。
2. ✅ **横向预览落法 B＋C 已确认**：App 内**不转屏**、画布按横向比例重排（落法 B）＋ HTML 导出带横向预设（落法 C）；**正式放弃落法 A（强制 App 转屏）** —— 不接系统方向、不改全局 `app.dart`，规避退出预览时的还原残留风险。
