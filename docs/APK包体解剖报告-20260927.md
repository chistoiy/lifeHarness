# APK 包体解剖报告 —— 模块插拔化调研（E 路线第一步）

- 日期：2026-09-27
- 性质：**纯只读分析**，未改动任何源码 / 构建配置 / 产物
- 对象：`lifeHarness-v1.45-douban-arm64.apk`（与 `build/app/outputs/flutter-apk/app-arm64-v8a-release.apk` 同一产物，mtime 2026-09-27 02:58，pubspec 版本 0.1.27+4025 线，DB schema v24）
- 方法：Python `zipfile` 逐条目枚举压缩前后字节，按目录/归属聚合（脚本为一次性工具，未入库）
- 背景：模块插拔化调研结论为「E 纯瘦身 → A 编译期变体 → D 原生 DSL 模块包」的顺序，本报告给出 E 的实测依据与 A 的立项参考数

## 一、总量构成（APK 35,537,437 B ≈ 33.9 MB）

| 归类 | 压缩后 | 占比 | 说明 |
|---|---:|---:|---|
| `libapp.so`（全部 Dart 代码 AOT） | 15.34 MB | 43.2% | 13 个 feature + core + 全部 Dart 三方包混在一处；Dart 侧未用的代码本会被 tree-shaking 剥掉，所以这 15 MB 是「全功能常驻」 |
| `libflutter.so`（Flutter 引擎） | 11.11 MB | 31.3% | 固定成本，任何路线都省不掉 |
| **mobile_scanner（MLKit 扫码）合计** | **≈5.86 MB** | **16.5%** | `libbarhopper_v3.so` 4.95 MB + `assets/mlkit_barcode_models/` 3 个 tflite 0.88 MB + `libimage_processing_util_jni.so` 32 KB |
| `classes.dex`（Java/Kotlin 插件壳） | 1.60 MB | 4.5% | 大头同样是 MLKit/play-services 包装层；压缩自 3.76 MB |
| `res/`（312 个文件）+ `resources.arsc` | 0.82 MB | 2.3% | 含品牌图标 PNG（最大单张 108 KB）等启动器资源 |
| KaTeX 字体（flutter_math_fork，20 个 ttf） | 0.37 MB | 1.0% | 仅 journal Markdown 数学渲染使用 |
| `MaterialIcons-Regular.otf` | 15 KB | – | 可再子集化，收益微小 |
| `NOTICES.Z`（开源声明） | 0.12 MB | 0.3% | 随依赖数变化 |
| 项目自有 assets（主题 JSON×10、AI prompts、习惯模板、导书模板） | < 20 KB | – | 可忽略 |

两个结构性事实：

1. **没有 CJK 字体进包**（走系统字体），所以「字体子集化」这条常见瘦身路在本项目基本无油水。
2. `.so` 均为未压缩存储（压缩前后相等），包内即装机体积，无解压摊销。

## 二、结论：谁在占包体

- **可移除的最大单项是 MLKit 扫码（16.5%）**，而它在本 App 只有一个消费点：`features/read/presentation/isbn_scan_page.dart:2`。呵护/记账/日记等全部模块对 webview、scanner、quill 均无引用（上一轮耦合调研已核实归属）。
- **webview_flutter 几乎不占包体**（渲染器由系统 Android WebView 提供，包内只有 dex 胶水），所以「豆瓣登录」不构成瘦身动机。
- **真正的「模块代码」在 `libapp.so` 里占多少，当前无法归因**——需要一次 `flutter build apk --release --analyze-size`（会产包体按 pub 包/模块的归属表）才能回答「核心版 APK 能小到什么程度」。这是 A 路线立项前的最后一个测量缺口。

## 三、行动清单（按投入产出排序，均不在本报告实施）

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| E1 | ISBN 扫码替换为轻量解码（zxing-cpp 级，纯 C++/Dart，无 MLKit） | **−5.9 MB（−17%）** | 只动 read 一个页面，识别率需真机对 ISBN-13/EAN-13 回归 |
| E2 | 若无数学公式刚需，移除 flutter_math_fork | −0.39 MB | journal md_view 公式能力下线，需产品拍板 |
| E3 | dex 侧 R8/keep 规则收缩 | −0.3~0.6 MB | 构建配置级，测试+冒烟可兜 |
| E4 | 跑一次 `--analyze-size` 归因 libapp.so | 测量，不省 | 无 |
| A | 据 E4 数据决定是否做编译期变体（核心版/加料版） | 视归因结果，核心版预估可至 18~24 MB | 解耦改造 3~5 周（见调研记忆） |

E1 一项就能把 33.9 MB 降到约 28 MB（−17%），且完全不触碰架构——这是「先 E 后 A」顺序的直接依据。

## 四、与模块插拔调研的衔接

- 本数据支持此前结论：**「禁用模块」在现状下零收益**（体积大头是引擎+Dart 全量+扫码原生库，与开关无关）；减体积只有两条真路——移除/替换特定重依赖（E1~E3），或编译期变体把 Dart 代码也拆走（A）。
- 备份/恢复层无需为 E 路线任何改动；若推进 A，`lh_bak.unpack` 对孤儿表/缺表的双向容忍已实测存在（`lib/core/backup/lh_bak.dart:469-541`），跨变体换机恢复兼容，仅建议补孤儿表清单与旧包迁移补跑两件事。
